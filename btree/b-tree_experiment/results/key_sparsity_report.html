Key 稀疏度與結構檢查的偵測範圍

B+ tree 的結構檢查不需要額外記憶體，但它能偵測多少 key 的位元翻轉，取決於 key 之間的間距。這份報告先量測這個關係，再比較各種補強方式。後半部只使用結構檢查本身：加強檢查規則、利用節點的空槽放 dummy key、把 key 映射到密集的範圍。

背景

為什麼 key 間距會影響偵測

結構檢查（SANITY）在每次讀取節點時確認幾項不變量，其中與 key 有關的一項是「節點內的 key 必須嚴格遞增」。一個 key 的某個位元被翻轉後，只要它仍然落在左右鄰居之間，遞增順序就沒有被破壞，結構檢查不會發現。

因此 key 間距為 2k 時，最低的 k 個位元翻轉都無法偵測，可偵測的比例約為 (64 − k) / 64。

內部節點存的是分隔 key（separator）。相鄰兩個 separator 的間距等於葉節點 key 間距乘上扇出，所以無法偵測的位元會再多 log₂(扇出) 個。這次實驗的節點平均裝 174 個 key，log₂ 174 ≈ 7.4。

偵測不到的位元在哪一層

這個實驗只對葉節點、或只對內部節點注入位元翻轉，再量測結構檢查對 key 每一個位元的偵測率。key 間距取 20（連續）、216、232 三種。

  • 葉節點無法偵測的位元數是 0、16、32，正好等於 key 間距的 log₂。
  • 內部節點無法偵測的位元數是 8、24、40，公式預測是 7.4、23.4、39.4。
  • key 完全連續時，葉節點的每個位元都能偵測，內部節點仍有 8 個位元偵測不到。

E12 · 50 runs

偵測不到的翻轉是否都會造成錯誤

沒有任何保護時，SDC 隨 key 變稀疏而下降，從 1.01×10−1 降到 2.4×10−2。這個實驗把錯誤答案分成三類，找出下降來自哪一類。

  • 下降全部來自「該找到卻找不到」這一類，平均從 2,719 降到 637。
  • 「找到但 value 錯誤」固定在 18 到 20 次，來自 values 被翻轉，與 key 分布無關。
  • 「不該存在卻找到」在所有間距都是 0。翻轉後的 key 並沒有被誤認成另一個存在的 key。

合理的解釋是：key 稀疏時，separator 的低位元翻轉只讓它在沒有 key 的空隙內移動，沒有任何實際存在的 key 會被導向錯誤的子樹。這與 E11 的結果一致（內部節點偵測不到的位元變多，但殘餘錯誤數沒有增加），不過沒有逐一事件驗證。

分層保護方案 HYBRID 的表現

HYBRID 把 CRC 只用在內部節點，葉節點只做結構檢查。它需要的可靠記憶體等於全部內部節點的 CRC 記錄大小。

HYBRID 的可靠記憶體396 B33 個內部節點 × 12 B。CTRL_CRC 需要 69,154 B，少 99.4%。
補上的 SDC 差距67% → 20%key 間距 20 到 232，以 SANITY 與 CTRL_CRC 的差距為 100%。
HYBRID 的平均延遲16.82 µs接近 CTRL_CRC 的 17.70 µs，高於 SANITY 的 15.13 µs。
  • 記憶體與 key 密集時的 SDC 符合預期。HYBRID 用 CTRL_CRC 的 0.6% 記憶體取得它三分之二的改善。
  • key 稀疏時不符合預期。稀疏 key 增加的 SDC 來自葉節點的 key 陣列，而 HYBRID 在葉節點只有結構檢查。
  • 延遲不符合預期。省下的只有葉節點那一次 CRC 計算。
  • 效果量很小。每個 run 相差 2 到 3 個錯誤答案。HYBRID 不高於 SANITY 在 25 組配對中成立 25 次（21 次較低、4 次相同）。

公式在真實的 key 分布下是否成立

固定間距是人工設定。這個實驗改用三類較接近實際資料的分布，並在每個 run 依實際的 key 集合算出公式預測值，再與實測比較。

分布說明
clustered1,000 個群，每群 1,000 個連號 key，群與群相距 232。類似多租戶的 ID 空間
geomgap 2k相鄰 key 的間距服從幾何分布，平均為 2k。平均與固定間距相同，但間距大小不一
random64均勻隨機的 64 位元 key。類似雜湊值或 UUID
  • 公式在五種分布上的誤差都不超過 2 個百分點。
  • 決定偵測比例的是平均間距。geomgap 與同平均的固定間距相差不到 0.6 個百分點。
  • 雜湊型 key 是最差情況。結構檢查只偵測到 CTRL_CRC 的三分之一，SDC 是它的兩倍。
  • 群集型 key 與連續 key 幾乎相同，因為大部分 key 的鄰居距離是 1。

扇出改變時規律是否成立

前面的實驗都使用 order 253。這個實驗在 200,000 個 key 下比較 order 16、64、253。

  • order 64 與 253 貼近公式，相差 1 到 7 個百分點。
  • order 16 在每個間距都只有公式的約 0.78 倍。可能原因是每個節點只有約 11 個 key，節點首尾的 key 只有一側有鄰居可比較，而且 SSD header 與 child pointers 佔 CTRL_CRC 涵蓋範圍的比例較高。這點尚未驗證。
E13 · 270 runs

插入 dummy key 能否補回偵測範圍

結構檢查看不到的翻轉，是 key 在空隙內移動而沒有越過鄰居。如果在真 key 旁邊緊貼著放一個不存放資料的 dummy key，真 key 一移動就會越過它，遞增順序被破壞，結構檢查就會報錯。這個做法不需要可靠記憶體，也不需要計算 CRC。

實驗把 dummy key 當成一般的 key 插入樹中，value 填入保留值，搜尋到 dummy key 視為找不到。比較四種放法：不放、只放右側 K+1、只放左側 K−1、兩側都放。另外加一組對照，把 dummy key 放在空隙正中間，樹同樣變大，但 key 旁邊沒有緊鄰的鄰居。

  • 兩側都放時，結構檢查抓到 97% 以上的真 key 翻轉。
  • 固定間距的 key 只放右側就夠，只放左側沒有效果。這種 key 的低位元全是 0，翻轉只會讓 key 變大。
  • random64 的位元是隨機的，單側各補回一半，兩側都放才完整。
  • 對照組只多 2 個百分點，表示效果來自緊鄰的鄰居，不是來自樹變大。
  • 把 dummy key 平均放在空隙裡，數量每加倍只多偵測 1 個位元，也就是 1.6 個百分點。低位元翻轉只讓 key 移動一點點，只有緊鄰的鄰居才會被撞到。
葉節點頁數2 到 3 倍單側 11,519 頁，兩側 16,970 頁。內部節點由 33 個變為 65 與 110 個。
右側 dummy 相對於對照組少 8.4 個樹大小相同時的比較。95% 信賴區間 4.8 到 13.0，五個 seed 都減少。
HYBRID 的「找不到」7.8 → 0.6內部節點有 CRC 時，葉節點 key 造成的錯誤幾乎消失。
  • 樹大小相同時，dummy key 有效。右側 dummy 比對照組每個 run 少 8.4 個錯誤答案，幾乎全部來自「找不到」。
  • 和原本的樹相比，只用結構檢查時沒有變好。合計由 28.6 變為 29.6 與 51.2。每頁的翻轉率固定，樹變大後翻轉總數等比增加，內部節點也變多，而結構檢查在內部節點上有偵測不到的位元。

把 CRC 存在頁面內

CTRL_CRC 與 FULL_CRC 把每個節點的 CRC 存在可靠記憶體。另一種做法是把 CRC 直接寫在頁面最後 4 bytes，讀取時重新計算並比對。這 4 bytes 本身也可能被翻轉，結果是比對不符，頁面從 SSD 重新載入，不會造成錯誤答案。

把 key 映射到密集的範圍

另一個方向是改變存進樹裡的 key，讓它們本身就是密集的，結構檢查自然恢復作用。做法依 key 是否有規律而不同。

key 的性質映射方式代價
固定間距 2k存入 key 除以 2k 的結果，變成連號無，順序保留
無規律以 hash 把每個 key 分配到一個小範圍內的格子，樹的 key 用格子編號。撞號時往下一格找要另存原本的 key，頁數約 2 倍，無法再依 key 的順序掃描

無規律的 key 塞進小範圍一定會撞號，所以每個 key 佔兩筆相鄰的資料，一筆存原本的 key，一筆存 value。查詢時把存著的原 key 重新 hash 一次，位置對不上就表示它被翻轉了。這個驗證只多一次 hash 計算。

  • 有規律的 key 換算成連號，效果最好而且免費。結果與原本就是連號的 key 逐欄相同。延遲略高是因為抓到並修復的翻轉變多。
  • hash 映射讓無規律 key 的「找不到」減少七成以上。由 14.8 降到 3.4 至 4.6。與同樣兩倍大的對照相比也顯著，所以不是樹變大造成的。
  • 代價是頁數 2 倍、延遲約 2.3 倍。每個 key 多存一筆原 key，撞號時要多找幾格，自我驗證每個 run 觸發約 1,600 到 2,100 次重新載入。
  • 範圍取多小沒有可分辨的差別。三種設定的差異在 seed 的誤差範圍內。查詢要找的格數與離線試算一致。
  • hash 映射必須搭配結構檢查。完全沒有檢查時，錯誤答案由 98.8 個增加到 1,100 個以上。

稀疏 key 下如何使用結構檢查

  • 結構檢查的偵測能力可以由 key 分布事先估計。連號或群集型 key 幾乎沒有盲區，間距 232 剩一半，雜湊型 key 剩三分之一。
  • 內部節點是最該補的地方，而且可以免費補上。內部節點的翻轉傷害是葉節點的 1340 倍以上，結構檢查在那裡固定有盲區。父子範圍檢查不多存任何東西，就讓內部節點造成的錯誤幾乎消失。
  • key 有固定規律時，稀疏的問題可以免費解決。檢查低位元或把 key 換算成連號，「找不到」回到連號 key 的水準。再加上範圍檢查與空槽 dummy key 後降到 0。
  • key 沒有規律時，需要付出成本。免費的做法只減少約三分之一，統計上不顯著。hash 映射減少七成以上，代價是頁數 2 倍、延遲約 2.3 倍，並失去依順序掃描的能力。
  • dummy key 要緊貼真 key 才有效，而且不能讓樹變大。平均放在空隙裡幾乎沒有效果。當成一般 key 插入會讓樹變成 2 到 3 倍，抵銷偵測率的提升。只用空槽時頁數不變，但只能覆蓋 45% 的 key。
  • value 錯誤是結構檢查的下限。value 沒有順序可言，任何結構規則都無法驗證它，每個 run 剩 15 到 21 個。
限制

解讀這些結果時要注意的事

  • 位元翻轉率 λ 比實際 DRAM 高出數個數量級，目的是在有限的操作數內取得足夠事件。
  • E11 只翻轉內部節點時，λ 再放大 50 倍，翻轉會在同一頁累積。跨層比較應使用「每次翻轉的錯誤數」，不應直接比較 SDC。
  • E10、E12、E13、E16 到 E21 每個設定 5 個 seed，E9 與 E11 為 3 個 seed。每個 run 相差 2 到 4 個錯誤答案的結果，應以配對檢定為準。
  • 範圍檢查能發現問題，但不一定能修復。壞掉的內部節點有時已經在節點分裂時被寫回 SSD，重新載入只會載回壞的版本。
  • 範圍檢查沒有抓到全部。只翻轉內部節點時，每 1000 次翻轉仍有不到 1 個錯誤答案。
  • hash 映射在 key 間距 232 的 5 個 run 中，有 1 個發生連續重新載入，錯誤答案 263 個，其餘 4 個為 16 到 25 個。原因尚未查明。
  • hash 映射的範圍大小必須事先依資料量決定。
  • E13 的 dummy key 走一般的插入路徑。樹變大是這種做法的代價，不是 dummy key 必然的代價。
  • E16 的結論只適用於單一位元翻轉、SSD 內容正確的錯誤模型。頁面整個被換成舊版本這類錯誤，頁內 CRC 無法偵測。
  • 工作負載固定為 90% 搜尋、10% 循序插入，翻轉只注入 DRAM。
  • E12 對 SDC 下降的解釋、E11 內部節點偵測率低於 100% 的原因、E9 order 16 偏低的原因、E13 的 value 錯誤隨樹變大而增加的原因，四者都是推測，沒有逐一事件驗證。
