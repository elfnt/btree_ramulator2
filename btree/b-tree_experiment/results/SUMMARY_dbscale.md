# Results Summary — DB 規模（E1′–E4′）與 `CTRL_CRC`

本檔是 `SUMMARY.md`（玩具規模：order 8 / 2000 keys）的**續集**，不是取代。
舊檔與 `e1.csv…e6b.csv` 原封保留為歷史基線；本檔的資料在
`e1_dbscale.csv`、`e2_dbscale.csv`、`e3_dbscale.csv`、`e4_dbscale.csv`、
`e1_dbscale_r2_noecc.csv`。

兩件新東西：

1. **DB 規模成為主要條件**，不再是舊 E6 那樣的側翼「密度軸」。
   order = 253（4096 B 頁 + 8 B key/value 塞得下的接近最大值：internal 節點
   32 + 253×8 + 254×8 = 4088 B）、1 000 000 keys、樹 ≈ 5 760 頁、高度 3。
2. **新增 `Scheme::CTRL_CRC`（控制平面 CRC）**，覆蓋
   `image[16 .. 16+ctrl_len)`，其中
   `ctrl_len = 16 + n_keys*8 + (internal ? (n_keys+1)*8 : 0)`——
   internal 節點等於整個節點內容，leaf 節點則是 header + keys[]、
   **刻意排除 values[]**。它填補的正是舊 `SUMMARY.md` 指出的洞：
   「HDR_CRC 把 would_crash 砍半，但 SDC 與 NONE 幾乎一模一樣」。

## 0. 規模校準（為什麼是 1M keys / 5 seeds）

先跑冒煙測試量真實吞吐再決定預算，而不是直接押上最大規模。
機器：32 核、59 GB RAM。單 run 峰值記憶體 ≈ 197 MB（故 26 路平行 ≈ 5 GB，安全）。

**ram 後端（`exp_fast.exe`），order = 253、n_ops = 30 000、λ = 3e-3：**

| prefill_keys | NONE 單 run wall |
|---|---|
| 100 000 | 0.79 s |
| 300 000 | 2.20 s |
| 1 000 000 | 7.65 s |

| scheme（prefill = 1M） | wall | scheme | wall |
|---|---|---|---|
| NONE | 7.65 s | CTRL_CRC | 24.4 s |
| SANITY | 8.82 s | FULL_CRC | 48.8 s |
| HDR_CRC | 8.70 s | FULL_CRC @ λ=3e-2（最壞） | 49.4 s |
| HDR_MIRROR | 8.51 s | CTRL_CRC @ λ=3e-2 | 25.0 s |

**r2 後端（`exp_r2.exe`，cycle-accurate DDR4，ECC off），prefill = 1M、λ = 3e-3：**

| scheme | wall |
|---|---|
| NONE | 15.1 s |
| CTRL_CRC | 31.3 s |
| FULL_CRC | 55.9 s |

r2 只比 ram 慢約 1.15–2 倍——遠比預期便宜，因為**平均 op 延遲被 SSD
write-through 主導**（10 % 的 insert 各付一次 `t_ssd` = 100 µs ≈ 10 µs/op），
DDR4 時序只影響其中很小一部分。這讓 r2 得以在 DB 規模跑完整的 E1′ 複本，
而不是像舊實驗那樣只能在玩具規模跑。

**因此選定的預算**（最壞情況 ~50 s/run、26 路平行）：

| | 掃描維度 | seeds | runs | 實際 wall |
|---|---|---|---|---|
| E1′ | 6 scheme × 7 λ | **5** | 210 | ~5 min |
| E2′ | 2 scheme × 4 policy × 9 budget | 3 | 216 | ~7 min |
| E3′ | 4 錯誤模式 × 6 scheme | 3 | 72 | ~3 min |
| E4′ | 2 scheme × 8 cadence | 3 | 48 | ~2 min |
| E1′-r2 | 6 scheme × 7 λ（ECC off） | 3 | 126 | ~5 min |

E1′ 用 **5 seeds**（歷史慣例是 3）：舊 `SUMMARY.md` 最大的資料品質警告就是
「NONE 的 `n_wrong_undetected` 逐 seed 極度離散（λ=1e-4 時 637/12/1，std > mean）」
——傷害由「flip 有沒有打中熱門內部節點」的樂透決定。既然 E1′ 是主表且成本低，
就多加 2 個 seed。**這仍不足以馴服該尾巴**（見資料品質警告 3）。

共用參數集中在 `scripts/db_common.sh`：
`--order=253 --prefill_keys=1000000 --n_ops=30000 --ssd_blocks=512
--ram_rows_per_bank=2048`（horizon = 30 000 × 0.01 = 300 模擬秒）。

## 1. 資料品質檢查

以 `python3 scripts/analyze_db.py <csv> --qc` 自動產生。

### 通過

1. **`fp = 0`**，全部 672 個 DB 規模 run——沒有任何誤報，precision 在有定義處恆為 1.0。
2. **歸因不變量成立**：`ctrl_only + payload_only + mixed + ssd_header == tp + fn`
   逐列吻合（四類互斥且窮盡）；`slack_only ⊆ payload_only` 亦逐列成立。
3. **`NONE` 恆 `n_wrong_undetected == n_wrong_total`**（從不報警 → 全部是 SDC）。
4. **`ram_misses = ram_lru_evictions = 0`**，全部 run——DRAM 容量 16 384 頁 >
   樹的 ~5 760 頁，全樹常駐，**自然清洗完全沒有介入**（與舊 E1/E2/E6 同條件，
   不會混淆 scheme 的比較）。
5. **`FULL_CRC`（budget=∞、EVERY_READ）恆 recall = 1.0、SDC = 0**，35 個 E1′ run
   全數成立，包含 λ=3e-2（~51 000 flips、19 827 次回復）。從未觀察到 CRC32 碰撞。
6. **樹形一致**：全部 run tree_height = 3、pages_allocated ∈ [5728, 5784]。
7. **`exp.exe`（asserts 全開）與 `exp_fast.exe`（-DNDEBUG）逐欄相同**：以
   CTRL_CRC、1M keys、λ=3e-3、seed 1 與 seed 2 各驗一次，59 個 CSV 欄位
   全部一致。故 E1′–E4′ 用 `exp_fast.exe` 產出的數字與 assert 版等價。
8. **`CTRL_CRC` 邊界自測**（driver 啟動時 `ctrl_crc_self_test()`，每個 run 都跑）：
   對 leaf/internal × n_keys ∈ {0,1,5,100,253}，驗證 (a) 乾淨往返不誤報、
   (b) `[16,16+ctrl_len)` 內**每一個** byte 翻轉都被抓到、
   (c) LEAF 在 `[16+ctrl_len, 4096)` 內**每一個** byte 翻轉都不被抓到。
   另以突變測試確認此自測有效：把 `ctrl_len` 公式改成漏掉 `children[]` 後
   重新建置，自測立刻 abort（`ctrl_len formula mismatch`）。

### 警告 / 異常

1. **`flip stream` 在 λ=3e-2 的 2/35 個 cell 跨 scheme 略有分歧**
   （seed 2：51 446 vs 51 454；seed 4：51 184 vs 51 204，差 ≤ 0.04 %）。
   成因同舊 `SUMMARY.md` 警告 1：Poisson 期望值取決於常駐頁數，而偵測/回復
   會微幅改變分裂時機。其餘 33 個 cell 逐列完全配對，跨 scheme 比較嚴格成立。

2. **⚠️ `results/SUMMARY.md` 的 E1 表與 `results/e1.csv` 不一致——舊表是陳舊的。**
   本次以現行程式重跑舊 E1 組態（order 8、2k keys、NONE、λ=3e-3、seeds 1–3），
   **逐 seed 完全重現 `e1.csv`**（wu = 88/39/54、flips = 717/791/813、
   poisoned = 1289/668/325）。但 `SUMMARY.md` 的 E1 表宣稱該格是
   SDC 5.2e-3（≈ wu 140）、poisoned 247、crash 1.7，
   而 `e1.csv` 實際是 SDC 2.23e-3、poisoned 761、crash 1.33。
   → **`e1.csv` 是可重現的權威資料；`SUMMARY.md` 的 E1 表不是。**
   本檔的「舊世界 vs DB 世界」對照一律引用 **CSV** 的值，不引用舊表的敘述。
   （E6 的情況相反，見警告 4。）

3. **NONE 系（NONE / HDR_CRC / HDR_MIRROR）的 SDC 在 λ ∈ [1e-3, 3e-3] 極度離散。**
   λ=1e-3 時 5-seed 的 `n_wrong_undetected` 平均 567.2、std 323；
   λ=3e-3 平均 2737.2、**std 2000（≈ 0.73 × mean）**；`would_crash` 更糟
   （57.4 ± 107）。機制是舊 `SUMMARY.md` E6 已指出的「內部節點樂透」：
   order 253 的 level-1 節點各覆蓋 ~43 000 個 key，一個 flip 打中它就會讓
   之後每次路由都可能走錯子樹。**5 seeds 沒有解決這件事**——
   這些格子的絕對值請當數量級讀，趨勢方向（NONE ≈ HDR_CRC ≫ CTRL_CRC）
   則完全穩健。相對地，`CTRL_CRC`/`SANITY`/`FULL_CRC` 的
   SDC std 都 ≤ 0.1 × mean。

4. **⚠️ `results/e6.csv` 無法在本機重現，且與程式版本無關。**
   以現行程式跑舊 E6 組態（NONE、λ=3e-3、seed 1）得
   pages 5776 / flips 5154 / wu 1601 / final_err 110 977；
   `e6.csv` 記錄的是 5780 / 5156 / 1483 / 86 268。
   為了排除「v2 迴歸」的可能，本次把 `e6.csv` 所屬 commit（`633ea0c`）的
   **整棵 v2 原始碼**匯出另外建置再跑同一組態——結果與**現行程式完全相同**
   （5776 / 5154 / 1601 / 110 977）。
   → **v2 沒有迴歸**；差異出在 `e6.csv` 當初的產生環境（極可能是不同平台的
   標準函式庫：`std::shuffle` 與 `std::uniform_int_distribution` 的輸出序列
   在 libstdc++ 與 MSVC 之間並不相同，prefill 的洗牌順序一變，
   樹的形狀就會差幾頁）。`SUMMARY.md` 的 E6 表**忠實反映 `e6.csv`**
   （flips 5154、final_err 95 256、crash 114、poisoned 1773 逐項吻合），
   但 `e6.csv` 本身在本機不可重現。
   → 因此凡需要嚴格 like-for-like 的比較，本檔一律用**本次重跑**的基線，
   而非 `e6.csv` 的絕對值。

5. **`n_poisoned_writes` 重尾且對 λ 非單調**（延續舊 `SUMMARY.md` 警告 2）：
   E1′ 的 CTRL_CRC 在 λ=1e-4 是 119.4 ± 267、λ=1e-3 是 509.2 ± 1131——
   std 遠大於 mean，因為單一 FN 讀落在不斷被重寫的最右插入路徑上就會引發連鎖。
   此指標衡量的是「哪一頁被打中」，不是 λ。

6. **`n_flip_events` 在 hammer / colfault 模式恆為 0**（該欄只計均勻 BER 的注入）。
   E3′ 沿用舊 `SUMMARY.md` E3 的慣例，以 **`FULL_CRC` 的 `n_recoveries`**
   當有效注入量的代理（colfault 恆為 512.0，與注入設計完全吻合）。

7. **`ssd_header` 桶不是「幾乎不會發生」**。設計預期是 `fill_ssd_header`
   每次寫入都會重寫 `[0,16)`，故該桶應趨近 0；實測在 `NONE` 下佔毀損讀取的
   0.2–1.7 %。原因是 flip 會打中 `[0,16)`（16/4096 = 0.39 % 的機率），
   而該頁在被重寫之前，每次讀取都會再記一次。這些位元組
   （SSD CRC 欄位、page_size 欄位）**實驗中從未被讀取**，故無害；
   但它們會被算成 FN，壓低 `CTRL_CRC` 的 recall（`CTRL_CRC` 的覆蓋從 offset 16
   起算，看不到它們）。這是 recall 這個指標的假影，不是方案的缺陷。

8. **分類優先序造成的輕微低估**：四類的判定順序是
   `ssd_header > mixed > ctrl_only > payload_only`。因此「同時打中 SSD header
   與控制平面」的讀取會被歸進 `ssd_header`，使
   「`CTRL_CRC` 原理上看得見的比例 = (ctrl_only + mixed)/corrupt」略為低估。
   影響上限即 `ssd_header` 的佔比（per-event 視角下 ≤ 1.0 %），不改變任何結論。

9. **兩後端的 DRAM 容量預設值差 8 倍（已規避，但值得記錄）**：
   不給 `--ram_rows_per_bank` 時，ram 後端得到
   `DRAM_NUM_BANKS(8) × (ssd_blocks·ppb/8) = 16 384` 頁，
   r2 後端卻只得到 `ssd_blocks·ppb/8 = 2 048` 頁。首次 r2 冒煙測試因此提早
   觸發 LRU 逐出（flips 1787 而非 5154，混入自然清洗）。
   **所有 DB 規模 run 一律顯式帶 `--ram_rows_per_bank=2048`**，兩後端同為
   16 384 頁；修正後 r2 的 `n_flip_events` 與 ram 後端逐格相同。

10. **`CTRL_CRC` 的 entry 帳面成本**：`scheme_entry_bytes` 回報 12 B/頁
    （與 HDR_CRC / FULL_CRC 相同，讓 E2′ 的 budget 軸可直接比較）。
    實作上另需存 2 B 的 `ctrl_len`，故嚴格計應為 14 B/頁。
    對 E2′ 的刻度影響 < 17 %，不影響任何定性結論，但引用絕對容量數字時應註明。

## 3. 毀損歸因：control-plane vs payload（Task 2 的證據實驗）

每次 `truth_corrupt` 的讀取都做位元組級 diff，以 **oracle**（地面真相）算出的
`ctrl_len` 為界分類。四類互斥窮盡；另記 `slack_only`
（`payload_only` 的子集：相異位元組全落在 `[16+live_len, 4096)` 的未使用補零）。

**讀 `FULL_CRC` 那幾列才是「每個毀損事件」的視角**：`FULL_CRC` 在第一次讀到
就偵測並回復，所以每個事件只被記一次。`NONE`/`HDR_CRC` 的毀損會持續存在，
每次重讀都再記一次，數字被讀取加權嚴重放大（λ=3e-2 時 2.78e6 vs 19 827，×140）。

**per-event 歸因（`FULL_CRC`，5 seeds）：**

| λ | 毀損事件數 | ctrl 可見 | 活 payload（values[]） | 無用 slack | ssd_header |
|---|---|---|---|---|---|
| 1e-5 | 18.6 | 36.1 % | 38.1 % | 24.7 % | 1.1 % |
| 1e-4 | 173.8 | 37.3 % | 32.5 % | 29.7 % | 0.46 % |
| 3e-4 | 508.4 | 34.5 % | 33.4 % | 31.6 % | 0.52 % |
| 1e-3 | 1 609.6 | 35.4 % | 34.6 % | 29.6 % | 0.40 % |
| 3e-3 | 4 489.8 | 38.5 % | 33.8 % | 27.3 % | 0.42 % |
| 1e-2 | 11 211 | 45.3 % | 32.3 % | 21.9 % | 0.58 % |
| 3e-2 | 19 826.8 | 58.2 % | 26.7 % | 14.0 % | 1.00 % |

幾何自洽性檢查：1M keys 分佈在 ~5 740 個葉節點 → 平均每葉 ~174 個 key
（order 上限 253）。一個滿的葉：ctrl = 16 + 174×8 = 1 408 B、
values = 1 392 B、補零 slack = 4096 − 16 − 1408 − 1392 = 1 280 B。
故均勻隨機 byte flip 落在 ctrl 的機率 ≈ 1408/4080 = **34.5 %**——
與 λ ≤ 1e-3 的實測 34.5–37.3 % 吻合。ctrl 佔比隨 λ 上升
（38.5 → 58.2 %）是因為高 λ 下同一頁累積多個 flip，
「至少有一個落在控制平面」的機率提高（`mixed` 從 6.2 % 漲到 39.7 %）。

**這張表的三個讀法：**

- **`CTRL_CRC` 原理上看得見的 = ctrl 可見欄**：在真實 DRAM 錯誤率的量級
  （λ ≤ 3e-3）約 **35–38 %**。
- **不保護 `values[]` 的真實代價 = 活 payload 欄**：約 **33 %**。
  這是「不動 values[] 就結構上無解」的部分。
- **另外約 27 % 是無用 slack**：那些位元組 B+ 樹永遠不會讀
  （節點只填到 `n_keys`），**語意上完全無害**。`FULL_CRC` 花成本去偵測並
  回復它們（這是它 recovery 數偏高的一部分原因），`CTRL_CRC` 正確地忽略它們。
  若不把 slack 從 `payload_only` 拆出來，會把「不保護 values[] 的代價」
  從 33 % 誇大成 61 %。

**為什麼「35 % 可見」卻換到「SDC −99 %」**：可見比例是按*毀損事件*算的，
SDC 是按*錯誤答案*算的，兩者權重完全不同。控制平面的毀損（尤其 internal
節點的 keys/children）會讓**每一次**路由經過都可能走錯子樹，一個事件製造
大量錯誤答案；而一個 leaf `values[]` 的毀損只毒害它自己那一筆 key。
E1′ 的 λ=3e-3：NONE 每 flip 傷害 0.527 個錯誤答案，`CTRL_CRC` 降到 0.0032
（×167）。**傷害是高度集中在控制平面的，即使控制平面只佔三分之一的毀損事件。**

**觀察：**

- **舊 E2 的「BY_LEVEL 在每個預算都贏」在 DB 規模仍然成立，而且贏得更誇張。**
  BY_LEVEL 用 **512 B（0.7 % 的全額預算）** 就把 SDC 從 1.147e-1 壓到
  1.505e-3（**−98.7 %，76 倍**），已達全額覆蓋（5.674e-4）的 2.7 倍以內。
  舊世界（order 8）要拿到可比的相對改善需要約 50 % 的預算。
- **膝點的位置有明確的機制解釋**：512 B = 42 個 entry ≥ 24 個 internal 節點。
  **一旦可靠記憶體裝得下整個上層控制平面，曲線就飽和**；256 B（21 entry）
  差一點裝完，SDC 就還在 1.74e-2（差 11.5 倍）。這是本實驗最可操作的結論：
  **order 越大，「保護全部 internal 節點」越便宜**——節點越滿，同樣的 key 數
  需要的 internal 節點越少，而它們正是傷害最集中的地方。
- **LRU 是第二名，但要 8 倍的預算**（4 096 B / 341 entry）才追平 BY_LEVEL 的
  512 B。機制：internal 節點每次搜尋都會被讀，所以只要 LRU 集合有幾百個
  entry，它們自然就一直待在裡面——LRU 是在「無意間」逼近 BY_LEVEL。
- **BY_HOTNESS 與 RANDOM 在小預算下幾乎無效**（≤ 1 024 B 時 SDC 仍
  1.11e-1 / 1.13e-1，相對 budget=0 只降 1–3 %）。BY_HOTNESS 的失效延續舊
  `SUMMARY.md` 診斷的無老化 LFU 病理：分裂後新生的 internal 節點以
  hotness = 1 進場，擠不掉早期就佔住位置的葉節點。
- **小預算時「選哪些頁」完全壓過「每頁保護多少」**：`CTRL_CRC` 與 `FULL_CRC`
  在 budget < 全額時逐格幾乎相同（差 ≤ 3 %），只有在全額覆蓋後才分出
  0 vs 5.674e-4。→ 預算受限時該投資的是 policy，不是更寬的 per-page 覆蓋。
- 資料品質：E2′ 全部 216 列 `fp = 0`、flip 流在 108 個 cell 全部逐列配對、
  無任何警告。

  （21/21 run）；`HDR_CRC` 的 SDC 在兩後端都與 `NONE` 幾乎完全相同；
  `CTRL_CRC` 在兩後端都把 SDC 壓到 1e-5–2.6e-3 的量級。
- **穩定的 scheme 跨後端吻合到個位數百分比**：`CTRL_CRC` 的 SDC 差距
  在五個 λ 分別是 −17 %、−10 %、+12 %、−2 %、+10 %；`FULL_CRC` 完全相同。
- **不穩定的 scheme 跨後端差很多，但那不是後端差異**：`NONE` 在 λ=1e-4
  是 1.48e-5（ram）vs 6.53e-3（r2），差 440 倍。這完全是資料品質警告 3
  的「內部節點樂透」——r2 該格的 std（±0.0113）比 mean（0.00652）還大，
  是單一 seed 打中熱門 internal 節點造成的。**不要把它讀成後端不一致。**
- **延遲幾乎相同（r2 一律低 0.2–0.4 %）**，雖然 r2 用的是真實 DDR4 時序而
  ram 用固定 `t_mem = 100 ns`。原因如校準節所述：平均 op 延遲被
  SSD write-through（10 % 的 insert × 100 µs）主導，DRAM 存取只佔很小一塊。
  → **想讓 DRAM 時序在本模型中顯著影響延遲，得先讓工作負載不是 write-through
  或把 `t_ssd` 調小**；目前的設定下 r2 的價值在於獨立驗證，不在於延遲數字。
- r2 的資料品質與 ram 同級：126 列 `fp = 0`、歸因不變量逐列成立、
  `ram_misses = 0`；僅 1/21 個 cell 有 ≤ 0.02 % 的 flip 流分歧。

## 9. Observations（總結）

1. **`CTRL_CRC` 補上了 `HDR_CRC` 留下的洞，而且幅度很大。**
   λ = 3e-3、DB 規模：`HDR_CRC` 的 SDC 是 1.013e-1，與 `NONE` 的 1.013e-1
   **在小數點後四位都相同**（−0.04 %）；`CTRL_CRC` 是 6.07e-4，
   **比 `HDR_CRC` 低 99.40 %**。final_err 從 113 383 降到 1 438（−98.7 %）。
   在 λ ∈ [1e-3, 3e-2] 的四個點，SDC 降幅一致落在 **−98.6 % ~ −99.4 %**。
   `HDR_MIRROR` 與 `HDR_CRC` 在 DB 規模仍然逐 seed 逐欄完全相同。

2. **代價是 `FULL_CRC` 的四成。** 純驗證地板（λ=1e-5，幾乎沒有回復）：
   `CTRL_CRC` +25.0 %（+2.62 µs）、`FULL_CRC` +61.7 %（+6.46 µs）——
   **41 %**。在 λ=3e-3 的工作點：+67.9 % vs +172.0 %（相對 NONE 的增量
   7.13 µs vs 18.06 µs，**39 %**）。這與 `ctrl_len/4096` 的幾何預期一致
   （讀取加權平均 ctrl_len ≈ 1 660–1 940 B）。
   → **`CTRL_CRC` 用 39–41 % 的成本買到 99 % 的 SDC 防護**；
   剩下那 1 % 要不要花 2.5 倍的錢買，是應用層的取捨。

3. **payload_only 有一半是假的——真正無解的是 33 %，不是 62 %。**
   按毀損事件計（`FULL_CRC` 視角，λ ≤ 3e-3）：控制平面可見 34.5–38.5 %、
   **活 `values[]` 32.5–34.6 %**、無用補零 slack 27.3–31.6 %、
   SSD header 0.4–0.5 %。
   order = 253 但平均每葉只裝 ~174 個 key，頁面約 31 % 是永遠不會被讀到的
   補零——落在那裡的 flip 會被 oracle 判為「毀損」，卻**語意上完全無害**。
   → 直接引用 `payload_only`（61–65 %）會把「不保護 `values[]` 的代價」
   誇大近一倍。**要保護 `values[]` 才能再進一步的部分是 ~33 %。**

4. **偵測面只涵蓋 35 % 的事件，卻擋掉 99 % 的錯誤答案——因為傷害極度不均勻。**
   控制平面的毀損（尤其 internal 節點的 keys/children）讓**每一次**路由都可能
   走錯子樹；一個 leaf `values[]` 的毀損只毒害它自己那一筆 key。
   λ=3e-3 的每 flip 傷害：`NONE` 0.527 個錯誤答案 → `CTRL_CRC` 0.0032（×167）。
   → **「保護多少位元組」和「擋掉多少傷害」不是同一件事**；
   B+ 樹的風險高度集中在控制平面。

5. **E3′ 用兩個欄故障實證了 `CTRL_CRC` 的邊界。** 同樣 512 個注入位元、
   同樣的空間結構，只差 byte 落在 keys[] 還是 values[]：
   控制平面欄故障（byte 128）下 `CTRL_CRC` **recall = 1.000、SDC = 0、
   final_err = 0，與 `FULL_CRC` 並駕**；payload 欄故障（byte 3000）下它幾乎
   全盲（recall 1.2e-6，SDC 只降 53 %）。**這是設計意圖的直接驗證**，
   也是第 3、4 點的機制層對應。

6. **空間叢發性的結論在 DB 規模反轉了。** 舊 E3 算出 colfault 每 flip 傷害
   是 uniform 的 **11.5 倍**；DB 規模剛好倒過來——uniform 0.693、hammer 0.247、
   colfault 0.011–0.016，**uniform 是 colfault 的 ~43 倍**。
   機制：舊樹 1 339 頁，512 列的欄故障汙染了全樹 38 %；DB 樹 5 763 頁，
   同樣 512 列只佔 8.9 %，而且葉節點裝 174 個 key（不是 5 個），
   單一 key byte 損壞只影響該葉 1/174 的鍵。
   → **樹夠大時，叢發性錯誤反而浪費在少數頁上；均勻錯誤才是最壞情況。**

7. **DB 規模下「保護全部 internal 節點」便宜到近乎免費。**
   h = 3 的樹只有 ~24 個 internal 節點；`BY_LEVEL` 用 **512 B**
   （42 個 entry，全額 69 312 B 的 **0.7 %**）就把 SDC 從 1.147e-1 壓到
   1.505e-3（**−98.7 %**），已在全額覆蓋的 2.7 倍以內。膝點的位置恰好是
   「可靠記憶體裝得下全部 internal 節點」那一格：256 B（21 entry）差一點裝完，
   SDC 還在 1.74e-2（差 11.5 倍）。舊 E2 的「BY_LEVEL 每個預算都贏」仍成立，
   但 DB 規模讓它贏得便宜太多。**LRU 要 8 倍預算才追平；
   BY_HOTNESS / RANDOM 在 ≤ 1 KB 幾乎無效。**
   小預算時「選哪些頁」完全壓過「每頁保護多少」——
   `CTRL_CRC` 與 `FULL_CRC` 的 budget 曲線在全額覆蓋前逐格幾乎相同。

8. **`SANITY`（0 可靠記憶體）在 DB 規模已經非常接近 `CTRL_CRC`，
   但差距隨 λ 拉開。** λ=3e-3：SDC 7.18e-4 vs 6.07e-4（`CTRL_CRC` 僅好 15 %）、
   延遲 +44.1 % vs +67.9 %——**在中等錯誤率下，免費的結構檢查幾乎打平
   花 12 B/頁 的 `CTRL_CRC`**。但 λ=3e-2 時 SANITY 退化到 1.008e-2
   （± 8.8e-3，極不穩定），`CTRL_CRC` 是 2.32e-3（±2.3e-4）——**好 4.3 倍
   且穩定 38 倍**；final_err 22 142 vs 3 240（好 6.8 倍）。
   → 誠實的取捨：**若目標錯誤率 ≤ 1e-2 flips/page/s，`SANITY` 的 CP 值極高；
   高錯誤率或需要可預測的尾部行為時才需要 `CTRL_CRC`。**
   兩者的 `would_crash` 在所有 DB 規模 run 都是 0（`HDR_CRC` 是 268.6 @ λ=3e-2）。

9. **`CTRL_CRC` 讓「週期驗證」這個旋鈕失去意義。** 放寬 θ 到極限，
   `FULL_CRC` 省 28.4 %（8.09 µs）、`CTRL_CRC` 只省 17.7 %（3.12 µs），
   而兩者付的偵測代價幾乎一樣（θ=100 時 SDC 3.181e-2 vs 3.225e-2）。
   每次驗證本來就便宜的方案，攤掉次數能省的自然少。
   → **用 `CTRL_CRC` 時膝點實質上就在 EVERY_READ。**
   另注意 `CTRL_CRC` 的 **recall 對 θ 幾乎不動（1.9e-3 → 1.4e-3）而 SDC 惡化
   57 倍**——它的 recall 分母被大量「看不見且無害」的 payload/slack FN 灌爆。
   **在這個 scheme 上 recall 是壞指標，SDC 才是對的指標。**

10. **`HDR_CRC` 在 DB 規模連 crash 紅利都沒了。** 舊世界它把 would_crash 砍半
    （1.33 → 0.67）；DB 世界只砍 6 %（57.4 → 54.0）。order 253 的節點裡
    固定 16 B 的 NodeHeader 只佔 0.39 %，而 keys[]/children[] 佔 34–99 %。
    **`HDR_CRC` / `HDR_MIRROR` 在真實 DB 節點密度下應視為無效方案。**

11. **Ramulator2 獨立佐證，但延遲維度資訊量有限。** 126 個 DDR4 run 重現了
    全部定性結論，穩定 scheme 的 SDC 跨後端差 ≤ 17 %。但兩後端的平均 op
    延遲只差 0.2–0.4 %，因為**延遲被 SSD write-through 主導**
    （10 % insert × `t_ssd` 100 µs ≈ 10 µs/op），DDR4 時序被淹沒。
    → 要讓 cycle-accurate 時序在結論中真正起作用，需要改工作負載
    （非 write-through、或調小 `t_ssd`）；目前 r2 的價值在獨立驗證。

### 尚未回答 / 值得後續

- **`CTRL_CRC` + `sanity_always` 的疊加**沒有跑。第 8 點顯示兩者的偵測面
  互補（SANITY 抓結構違反、CTRL_CRC 抓任意控制平面位元），疊加成本幾乎為零
  （`t_sanity` = 50 ns），很可能是最佳 CP 值點。
- **`values[]` 的分層保護**：第 3 點量出還有 ~33 % 的毀損需要保護 `values[]`
  才擋得住。一個「CTRL_CRC + 只對熱門葉節點做 FULL_CRC」的混合方案值得試。
- **NONE 系的重尾**（資料品質警告 3）需要 ≫ 5 seeds 才能給出可信的信賴區間；
  目前這些格子只能當數量級讀。
- 本批全部是**全樹常駐、無自然清洗**的條件。舊 E5 顯示縮小 RAM 會大幅改變
  `NONE`/`SANITY` 的相對優劣；`CTRL_CRC` 在 RAM 受限下的表現未測。

## 10. E5′ — 受限 RAM 與自然清洗（DB 規模，λ = 3e-3、EVERY_READ、5 seeds）

本節接續 §9「尚未回答」的最後一項：**E1′–E4′ 全部是「全樹常駐、零自然清洗」的
條件，`CTRL_CRC` 在 RAM 受限下沒測過**。資料在 `results/e5_dbscale.csv`
（140 列 = 4 scheme × 7 rpb × 5 seeds），腳本 `scripts/run_e5_db.sh`。

舊 `SUMMARY.md` 的 E5（order 8、2 000 keys、~1 348 頁）發現：縮小 RAM → LRU
逐出 → 未偵測的毀損頁在被重複讀到之前就被丟棄、下次 miss 時從乾淨 SSD 重載
＝ **免費的「自然清洗」**；SDC/flip 從 0.182 掉到 0.004（rpb=32），代價是平均
延遲 19.6 → 153.7 µs。同時發現 `FULL_CRC` 的相對成本被 SSD miss「吸收」到
只剩 +7 %。本節問兩件事：**(a) 這個清洗效應在 DB 節點密度下還在嗎？
(b) `CTRL_CRC` 相對 `FULL_CRC` 的成本優勢在 RAM 壓力下還剩多少？**

### 10.0 規模校準（為什麼是這七個 `ram_rows_per_bank`）

（容量 = 8 × rpb = 4 096…128 頁，即樹的 3.06× … 0.096×）。DB 樹是 ~5 776 頁，
同一組 rpb 有五分之四會落在「完全常駐」那一側。本節改成**對齊容量/樹大小的比值**
重挑，並先用冒煙測試確認每一格真的落在預期的逐出強度上。

### 10.1 資料品質檢查

**通過**

1. **`fp = 0`**，全部 140 列。
2. **歸因不變量成立**（`ctrl_only+payload_only+mixed+ssd_header == tp+fn`）逐列吻合；
   `slack_only ⊆ payload_only` 逐列成立。
3. **`NONE` 恆 `n_wrong_undetected == n_wrong_total`**。
4. **`FULL_CRC` 在全部 35 個 run 都是 recall = 1.0、SDC = 0、final_err = 0**——
   **包含最重度逐出的 rpb=32**。這一點很重要：它證明 RAM 壓力沒有破壞任何
   偵測/復原路徑，因此各 scheme 的比較仍然成立。
5. **flip 流逐格嚴格配對**：以 (rpb, seed) 為格，35 格**全部**四個 scheme 的
   `n_flip_events` 完全相同（0 格分歧）。跨 scheme 比較是嚴格配對的。
   ⚠️ **`scripts/analyze_db.py --qc` 會對本檔誤報 5/5 格分歧**——它的配對鍵
   （`qc()` 裡的 `keys` 清單）**沒有包含 `ram_rows_per_bank`**，於是把七個不同
   容量的 cell 混成同一格比較。這是分析腳本的漏洞、不是資料問題；上面的
   0/35 是以正確分組獨立重算的。（未修改 `analyze_db.py`，僅在此記錄。）
6. **樹形一致**：全部 run tree_height = 3、pages_allocated ∈ [5 729, 5 784]，
   與 E1′ 同區間——縮小 DRAM 沒有改變樹的形狀，只改變常駐集合。
7. **常駐頁數與容量吻合到 1 %**：由 `n_flip_events / (λ · dt · n_ops)`
   = `flips/0.9` 反推的主迴圈平均常駐頁數為
   5 772 / 5 768 / 4 066 / 2 009 / 1 021 / 513 / 259（rpb 2048→32），
   對應容量 16 384（受樹的 5 776 頁封頂）/ 5 760 / 4 096 / 2 048 / 1 024 / 512 / 256。
   **每一格 RAM 都確實被填滿並持續逐出**，這是「真的有 RAM 壓力」的直接證據。

**警告 / 異常**

1. **⚠️ `ram_misses` / `ram_lru_evictions` 這兩欄被最終完整性掃描主導，
   不能當成「主迴圈的逐出強度」讀。** 三個獨立證據：
   (a) `ram_baseline` 在 prefill 後取快照，故這兩欄涵蓋**主迴圈 + 完整性掃描**，
       而掃描是 1.03 M 次 search（占全部 guarded read 的 99.7 %）；
   (b) 由延遲反推的主迴圈 miss 只有 6 970–24 625（見 §10.0 表），
       而報告值是 5.3e5–2.9e6 —— **95–99 % 的計數來自掃描**；
   (c) 掃描期間 `tree.advance_time()` **不會被呼叫**（見
       `src/main_experiment.cpp` 的完整性掃描迴圈），模擬時鐘凍結在 300 s，
       於是所有被觸碰的 slot 的 `last_access` 全部相等，v2 `RAM::do_evict_lru()`
       的嚴格 `<` 比較在全平手時固定選中**物理索引最小的 valid slot**，
       LRU 退化成「(容量−1) 個凍結頁 + 1 個輪替 slot」。
   實測佐證：λ=0、`n_ops=100`（時鐘只推進到 1 s）時 rpb=128 的 miss 是
   **1 588 585**；同樣 rpb、`n_ops=30000`（時鐘推進到 300 s）時是 **1 609 459**，
   而在有毀損、搜尋路徑塌縮的 seed 1 上掉到 **4 070**（見警告 3）。
   → **這是 harness 既有的性質（v2 為唯讀相依，未修改）**，不影響本節的主結論，
   因為 **SDC（`n_wrong_undetected`）、平均延遲、`n_flip_events` 三者都只在主迴圈
   計數**（`metrics.add_op_latency` 與 `n_searches` 只在主迴圈遞增、
   `FaultInjector::advance` 只在主迴圈呼叫）。受影響的是
   `ram_misses`/`ram_lru_evictions`/`n_recoveries`/`n_final_integrity_errors`
   四欄的「掃描分量」。表中兩欄仍**照實登載**（下游報告需要完整資料），
   但解讀主迴圈壓力時請用 §10.0 的「主迴圈 miss 推估」。

2. **`n_final_integrity_errors` 在 rpb 受限時同時混入「掃描期重載」**：
   掃描讀到一頁 → miss → 從 SSD 重載乾淨副本 → 該 key 就不算錯。
   所以 `NONE` 的 final_err 隨 RAM 縮小而下降（113 585 → 12 272）有一部分
   不是主迴圈的清洗，而是掃描自己把資料修好了。**SDC 沒有這個問題**
   （主迴圈的 search 對照 `std::map`，當下就判定）。

3. **`NONE` @ rpb=128、seed 1 是本節唯一的離群格**：`wu = 18 030`
   （另四 seed 為 116 / 601 / 960 / 1744）、`final_err = 834 564`、
   平均延遲 23.9 µs（另四 seed 74.8–80.3 µs）、`ram_misses` 4 070（另四 seed
   ~1.5 M）。機制是資料品質警告 3 的「內部節點樂透」極端形式：某個 level-1

### 10.5 觀察

- **`CTRL_CRC` 在 RAM 受限下升級成「與 `FULL_CRC` 等價」。**
  rpb ≤ 128（容量 ≤ 樹的 17.7 %）時 `CTRL_CRC` 的 SDC = **0、wu = 0、
  final_err ≤ 0.8、would_crash = 0，5 seeds 全部**，與 `FULL_CRC` 並駕，
  而延遲只差 4.0–4.8 %。全常駐時它們的差距是 SDC 6.07e-4 vs 0、延遲差 62 %。
  → **RAM 越緊，`CTRL_CRC` 越划算；在 RAM 受限系統上它幾乎沒有理由被 `FULL_CRC` 取代。**
- **這不是因為 RAM 壓力把毀損洗掉了，而是因為它把毀損推進控制平面。**
  §10.3 的兩張表是同一件事的兩面：`NONE` 的 SDC/flip 惡化 9.5 倍
  （0.527 → 4.99）、`CTRL_CRC` 的 SDC/flip 改善到 0——因為 ctrl 可見的
  事件比例從 38.5 % 升到 66.0 %、活 payload 從 33.8 % 掉到 3.9 %。
- **「自然清洗是免費防護」這個舊結論在 DB 規模不成立。** 舊 E5（order 8、
  1 348 頁）SDC/flip 0.182 → 0.004（清洗贏）；DB 規模 0.527 → 4.99（瞄準效應贏）。
  差別在**內部節點的稀有度**：order 8 / h=5 的樹裡 internal 節點約佔 18 %，
  縮小 RAM 不會顯著改變它們在常駐集合中的比例；order 253 / h=3 的樹只有
  ~24 個 internal（0.42 %），縮到 256 頁時它們變成常駐集合的 ~9 %，
  **濃度提高 22 倍**。→ **節點越密、樹越淺，「靠逐出來清洗」越不可行。**
- **清洗的吞吐代價在 DB 規模比舊世界更陡。** `NONE` 平均 op 延遲
  10.50 → 89.01 µs（**8.5×**，與舊 E5 的 7.8× 同級），但基線只有 10.5 µs
  （舊世界 19.6 µs），所以**同樣的絕對延遲買到的保護少得多**：
  舊世界拿到 SDC −95 %，DB 世界只拿到 −58 %（1.013e-1 → 4.30e-2），
  而且 SDC/flip 還變差。→ **在 DB 規模，「砍 RAM 換可靠性」是純虧的交易；
  同樣的錢拿去買 `CTRL_CRC`（+67.9 % 延遲、SDC −99.4 %）好太多。**
- **`SANITY` 在 RAM 壓力下也會收斂到近乎完美**（rpb=32：SDC 1.48e-5、
  final_err 0.2），而且它的絕對延遲在每一格都比 `CTRL_CRC` 低 2.47–2.50 µs。
  但它在中等壓力區（rpb 512–128）仍比 `CTRL_CRC` 差 1.3–∞ 倍
  （4.74e-4 vs 3.63e-4；1.26e-4 vs 0），且 5-seed 標準差常大於平均值
  （rpb=128：1.258e-4 ± 1.8e-4）。**延續 §9 第 8 點的取捨：要可預測的尾部就用
  `CTRL_CRC`。**
- **`would_crash` 在 `CTRL_CRC` / `SANITY` 的全部 70 個 run 都是 0**；
  `NONE` 在每一格都非零（33.4–93.4），且**不隨 RAM 縮小而消失**
  （rpb=64 的 93.4 是全表最高）——與 SDC/flip 上升同源。
- **`FULL_CRC` 的 `n_recoveries` 隨曝險線性縮**（4 489.8 → 30.6，比值
  0.86 : 0.85 : 0.48 : 0.22 : 0.13 : 0.10 : 0.13 相對 flips），
  rpb=32 時 86.9 % 的 flip 在被重讀到之前就已被逐出——這才是「清洗」真正的量。
  它清掉的絕大多數是無害的 slack/payload flip（見 §10.3 歸因表），
  留下來的偏偏是 internal 節點的那些。

## 11. E6a′ — 節點密度軸（200 000 keys、order ∈ {8,32,128,253}、λ = 3e-3、5 seeds）

資料在 `results/e6a_dbscale.csv`（80 列 = 4 order × 4 scheme × 5 seeds），
腳本 `scripts/run_e6a_db.sh`。

**為什麼不是照抄舊 E6b。** E1′–E4′ 已把 order=253 / 1M keys 當成**預設條件**，
再掃一次同樣的 order 軸只是重覆已知結果。E6a′ 改問一個只有 `CTRL_CRC` 才問得出的
問題：**`CTRL_CRC` 的整個賣點是「保護 control plane、跳過 `values[]`」，
但一個 4096 B 頁裡 control : payload : slack 的位元組比例本身隨 order 大幅變動——
那 `CTRL_CRC` 的優勢會不會只是 order=253 的特例？**
scheme 換成 {NONE, HDR_CRC, CTRL_CRC, FULL_CRC}：這裡要的是
「`CTRL_CRC` 補上了 `HDR_CRC` 多大的洞」隨密度怎麼變，`HDR_CRC` 是必要的對照。

### 11.1 資料品質檢查

**通過**：`fp = 0`（80/80）；歸因不變量逐列成立；`slack_only ⊆ payload_only`；
`NONE` 恆 `wu == wrong_total`；**`ram_misses = ram_lru_evictions = 0`（80/80，
全樹常駐確認）**；`FULL_CRC` 在 20/20 個 run recall = 1.0、SDC = 0；
tree_height ∈ {7, 4, 3, 3}（order 8/32/128/253）、pages 1 111–42 331。

**警告**：
1. **flip 流在 1/20 格分歧**（order 128、seed 3：2 015 vs 2 017，差 0.1 %）——
   成因同 E1′ 警告 1（偵測/回復微幅改變分裂時機）。其餘 19 格逐列配對。
2. **`NONE` 的絕對值在每個 order 都是樂透**（延續 E1′ 警告 3）。
   per-seed `wu`：order 8 = 137/307/185/166/267；order 32 = 99/376/190/878/425；
   **order 128 = 1128/332/608/338/3802**（std 1 490 > mean 1 242）；
   order 253 = 187/68/140/279/40。→ **`NONE` 的跨 order 比較只能讀數量級**；
   本節的結論一律建立在 `CTRL_CRC` 自己的數字（每個 order 都很緊：
   `wu` 全部落在 12–27）與**逐 seed 配對**的 `HDR_CRC` → `CTRL_CRC` 降幅上。

### 11.2 控制平面 / payload / slack 的位元組幾何隨 order 怎麼變

實際公式（`src/shadow_store.cpp` 的 `ctrl_len_of` / `live_len_of`，已核對過原始碼）：

```
leaf     : ctrl_len = 16 + n_keys*8                    live_len = ctrl_len + n_keys*8
internal : ctrl_len = 16 + n_keys*8 + (n_keys+1)*8     live_len = ctrl_len
           = 24 + 16*n_keys
覆蓋區 = image[16 .. 16+ctrl_len)，頁面可變動位元組共 4096 − 16 = 4080 B
```

### 11.4 觀察

- **`CTRL_CRC` 的優勢**不是**DB 規模的特例——它在整條密度軸上都成立，
  而且低 order 時反而更強。** `CTRL_CRC` 在四個 order 都把 `wu` 壓到
  **18.6–22.4**（`HDR_CRC` 是 142.8–1 242），SDC 全部落在
  **6.88e-4 – 8.29e-4** 的窄帶裡；而它的成本佔 `FULL_CRC` 的比例是
  **2.4 % → 6.7 % → 20.0 % → 34.3 %**。
  → **order 253（真實 DB 密度）其實是 `CTRL_CRC` 成本上最不利的一端**；
  在稀疏節點的樹上它幾乎是免費的（+6.2 % vs `FULL_CRC` 的 +261.8 %）。
- **成本比完全由幾何決定，可以直接預測。** 成本比 ≈ 讀取加權平均
  `ctrl_len` / 4096：預測 2.4 / 8.1 / 20.6 / 36.7 %，實測 2.4 / 6.7 / 20.0 / 34.3 %。
  → 要估任何新 order 的 `CTRL_CRC` 成本，不必跑實驗，算 `ctrl_len` 就好。
- **`FULL_CRC` 在低密度樹上是災難性地貴。** order 8：+261.8 %（20.06 → 72.58 µs），
  因為 h=7 意味著每次搜尋要對 **7 個 4096 B 頁**各做一次全頁 CRC，
  而其中 **96 %** 的位元組是永遠不會被讀到的補零（§11.2）。
  `CTRL_CRC` 對同一棵樹只算 ~100 B/讀。
  → **節點越空，「保護整頁」越荒謬。**
- **`HDR_CRC` 的 crash 紅利隨密度單調蒸發，這次量到了完整曲線。**
  would_crash 相對 `NONE`：order 8 **−45.4 %**（89.0 → 48.6）、
  order 32 −35.9 %（20.6 → 13.2）、order 128 −40.0 %（5.0 → 3.0，n 太小）、
  **order 253 −2.6 %**（31.0 → 30.2）。
  舊 `SUMMARY.md`（order 8）量到 −50 %、E1′（order 253/1M）量到 −6 %，
  本表把中間的梯度補齊了：**16 B 的 NodeHeader 佔頁面比例（0.39 % @ order 253
  vs 有效內容的 26 % @ order 8）就是這條曲線。**
  `CTRL_CRC` 在**四個 order 的全部 20 個 run** would_crash = 0（E5′ 的 35 個、
  E6b′ 的 20 個亦然）。
- **可靠記憶體成本在四個 scheme 之間完全相同，差別純粹在驗證時間。**
  `shadow_bytes_used_max` 逐 order 為 507 478 / 114 48x / 27 61x / 13 524 B，
  `HDR_CRC`/`CTRL_CRC`/`FULL_CRC` 三者相同（12.00 B/頁，差異 ≤ 5 B 來自
  各 run 頁數微差）。→ **E2′ 的 budget 軸對三者刻度一致；`CTRL_CRC` 買到的
  99 % SDC 防護在「可靠記憶體容量」這個維度上是完全免費的**，
  代價全部記在延遲上。
  （沿用 §1 警告 10：實作另需 2 B 存 `ctrl_len`，嚴格計為 14 B/頁，+16.7 %。）
- **`CTRL_CRC` 的偵測覆蓋率（recoveries/flips）＝ 它的幾何覆蓋率**：
  1.64 / 4.92 / 17.60 / 35.43 %（order 8→253），對照 §11.2 的 ctrl 可見比例
  2.20 / 5.91 / 18.84 / 36.75 %。`FULL_CRC` 是 74.5 / 83.1 / 93.3 / 96.4 %。
  → **在 order 8，`CTRL_CRC` 只攔下 `FULL_CRC` 的 2.2 % 的事件，卻擋掉了
  89.4 % 的錯誤答案**——§9 第 4 點的「傷害極度不均勻」在低密度下更誇張。
- **`poisoned writes` 的密度趨勢在 200k 規模不重現。** 舊 E6b（50k keys）觀察到
  `NONE` 的 poisoned 隨 order 單調爆炸（199 → 1 950）；本節是
  1 806 / 82.2 / 1 775 / 955（order 8→253），非單調。逐 seed 檢查顯示這欄
  被少數幾個「打中最右插入路徑」的事件支配（延續 §1 警告 5）。
  → **這欄在任何規模都只能當數量級讀，舊 E6b 的單調趨勢不應被當成結論。**

### 12.3 觀察

- **E1′ 的頭條結論在 25 倍的規模跨度上穩健，只有溫和漂移。**

  隨規模上升，`CTRL_CRC` 的相對便宜度就被稀釋。
  → **在 order 253 這條軸上，`CTRL_CRC` 的成本比會漸近到約 45 %，不會再壞下去；
  它不是 1M 這一個點的巧合。**
- **`CTRL_CRC` 的 SDC 幾乎完全不隨規模變動：6.07e-4 – 7.92e-4，跨 25 倍規模

  **這是本節最乾淨的結果：`CTRL_CRC` 把「這棵樹有多大」這個變數從 SDC 裡拿掉了。**
- **`FULL_CRC` 在 5M keys / 26 423 flips / 19 350 次回復下仍然完美**
  （20/20 run recall = 1.0、SDC = 0、final_err = 0、would_crash = 0、
  poisoned = 0、fp = 0）。從未觀察到 CRC32 碰撞。
- **「內部節點樂透」的重尾在 ≥ 3M keys 開始自己收斂。**
  `NONE` 的 SDC std/mean：200k = 0.66、1M = **0.73**、3M = **0.22**、5M = **0.22**。
  機制：h=3 的樹在 1M 時只有 ~23 個 level-1 internal 節點，單一節點被打中就能
  支配整個 run；5M 時有 ~169 個，單點事故被平均掉。
  → **§1 警告 3 的「5 seeds 沒有馴服這條尾巴」有解，但解法不是加 seed，
  是把樹做大。** 想要 `NONE` 的可信賴區間，跑 3M–5M 比跑 20 個 seed 便宜。
- **`NONE` 的每 flip 傷害隨規模單調下降**（0.1428 → 0.5269 → 0.0888 → 0.0742；
  1M 那點被樂透抬高，其餘三點單調）。機制與 §4 的「叢發性錯誤在大樹被稀釋」
  同源：樹越大，單一損頁在 27 040 次查詢裡被讀到的機率越低。
  但**絕對 final_err 仍隨規模爆炸**（3 067 → 699 418，×228），
  因為完整性掃描的分母也大了 25 倍。
- **延遲基線完全平坦**（`NONE` 10.484 → 10.530 µs，跨 25 倍規模差 0.4 %），
  因為 h 恆為 3、且平均 op 延遲被 SSD write-through 主導（§8）。
  所有 overhead 的成長都來自 CRC 驗證與回復，不是樹變大本身。

## 13. Observations（E5′–E6b′ 補充，接續 §9）

12. **`CTRL_CRC` 在 RAM 受限下升級成與 `FULL_CRC` 等價。**
    容量 ≤ 樹的 17.7 %（rpb ≤ 128）時，`CTRL_CRC` 的 SDC = 0、wu = 0、
    final_err ≤ 0.8、crash = 0，**5 seeds × 3 個容量共 15 個 run 全部**，
    而延遲只比 `FULL_CRC` 低 4.0–4.8 %。全常駐時兩者是 SDC 6.07e-4 vs 0、
    延遲差 **+62.0 %**。→ **RAM 越緊，`CTRL_CRC` 越沒有被取代的理由。**

13. **「縮小 RAM = 免費的自然清洗」這個舊結論在 DB 節點密度下反轉了。**
    舊 E5（order 8、1 348 頁）：SDC/flip 0.182 → 0.004（清洗贏 42 倍）。
    DB 規模（order 253、5 776 頁）：SDC/flip **0.527 → 4.99（惡化 9.5 倍）**。
    原始 SDC 之所以仍下降（1.013e-1 → 4.30e-2）純粹靠曝險少了 22 倍在硬撐。
    機制：h=3 的樹只有 ~24 個 internal 節點（全樹的 0.42 %），但它們每次搜尋
    都被讀 → 永遠留在 LRU 集合裡；容量縮到 256 頁時它們變成常駐集合的 ~9 %，
    **濃度提高 22 倍**，而它們正是唯一「毀損後每次路由都再犯一次錯」的頁。
    → **RAM 壓力不是清洗，是把故障瞄準到最危險的頁上。**

14. **同一個瞄準效應對 `CTRL_CRC` 是純利多，這是 12 與 13 的共同機制。**
    per-event 歸因隨容量縮小的移動（`FULL_CRC` 視角）：
    ctrl 可見 38.5 % → **66.0 %**、活 `values[]` 33.8 % → **3.9 %**
    （容量 16 384 → 256 頁）。**RAM 壓力把毀損推進 `CTRL_CRC` 的守備範圍，
    同時把它唯一的盲區抽乾。**

15. **在 DB 規模，「砍 RAM 換可靠性」是純虧的交易。**
    `NONE` 平均延遲 10.50 → 89.01 µs（**8.5×**）只換到 SDC −58 %，
    而且每 flip 傷害還惡化 9.5 倍；同樣一筆錢買 `CTRL_CRC`
    （+67.9 % 延遲、SDC −99.4 %、crash 0）好一個數量級以上。
    舊世界的「用 8 倍延遲換 SDC −95 %」在這裡不再成立。

16. **`CTRL_CRC` 的優勢不是 DB 規模的特例：它在整條密度軸上都成立，
    而且 order 253 其實是它成本上最不利的一端。**
    `CTRL_CRC` 佔 `FULL_CRC` 的成本：order 8 = **2.4 %**、32 = 6.7 %、
    128 = 20.0 %、253 = 34.3 %（200k keys）。
    同時它在四個 order 都把 `wu` 壓到 18.6–22.4、SDC 落在 6.88e-4 – 8.29e-4
    的窄帶，相對 `HDR_CRC` 的降幅 −87.0 % ~ −98.5 %。
    → **越稀疏的樹，`CTRL_CRC` 越接近「免費」。**

17. **成本比可以純用幾何預測，不必跑實驗。**
    `CTRL_CRC` overhead / `FULL_CRC` overhead ≈ 讀取加權平均 `ctrl_len` / 4096：
    預測 2.4 / 8.1 / 20.6 / 36.7 %（order 8/32/128/253），
    實測 **2.4 / 6.7 / 20.0 / 34.3 %**。同一個公式也對上規模軸
    （200k → 5M 的 34.3 → 44.5 %，因為 h 不變而 root/level-1 被塞得更滿）。

18. **`FULL_CRC` 在低密度樹上貴到荒謬，因為它保護的多半是不存在的資料。**
    order 8、200k keys：+261.8 %（20.06 → 72.58 µs），h=7 → 每次搜尋要對
    7 個 4096 B 頁各做一次全頁 CRC——而其中 **96.0 %** 的位元組是
    永遠不會被讀到的補零。`CTRL_CRC` 對同一棵樹只算約 100 B/讀。

19. **`HDR_CRC` 的 crash 紅利隨節點密度單調蒸發，完整曲線已量到。**
    would_crash 相對 `NONE`：order 8 **−45.4 %** → 32 −35.9 % → 128 −40.0 %
    （n 太小）→ 253 **−2.6 %**。這條曲線就是「16 B 的 NodeHeader 佔頁面有效
    內容的比例」（order 8 約 26 %、order 253 約 0.39 %）。
    `CTRL_CRC` 在 E5′+E6a′+E6b′ 的**全部 75 個 run** would_crash = 0。

20. **`CTRL_CRC` 買到的防護在「可靠記憶體容量」這個維度上完全免費。**
    `shadow_bytes_used_max` 在 `HDR_CRC`/`CTRL_CRC`/`FULL_CRC` 三者於每個 order
    都相同（12.00 B/頁；order 8 = 507 478 B、253 = 13 524 B）。
    差別 100 % 記在延遲上。（嚴格計 `CTRL_CRC` 另需 2 B 存 `ctrl_len` → 14 B/頁。）

21. **E1′ 的頭條結論在 200k – 5M keys（25 倍跨度）穩健。**
    `CTRL_CRC` 的 SDC 只在 **6.07e-4 – 7.92e-4** 之間動（差 30 %），
    `NONE` 卻在 5.285e-3 – 1.013e-1 之間動（差 19 倍）。
    成本比溫和上升到約 45 % 後趨於平緩。`FULL_CRC` 在 5M keys /
    26 423 flips / 19 350 次回復下仍 20/20 run 完美。

22. **「內部節點樂透」的重尾靠把樹做大就會自己收斂，不必加 seed。**
    `NONE` 的 SDC std/mean：200k = 0.66、1M = 0.73、**3M = 0.22、5M = 0.22**。
    1M 的 h=3 樹只有 ~23 個 level-1 internal，單點事故支配整個 run；
    5M 有 ~169 個就平均掉了。→ 想要 `NONE` 的可信賴區間，
    **跑 3M–5M 比跑 20 個 seed 便宜**（§1 警告 3 的實際解法）。

23. **⚠️ 方法論限制（新發現，未修正，影響範圍已界定）：
    最終完整性掃描在「凍結的模擬時鐘」下執行，會讓 v2 `RAM` 的 LRU 退化。**
    `src/main_experiment.cpp` 的掃描迴圈只呼叫 `note_op_boundary()`，
    不呼叫 `advance_time()`，所以 1.03 M 次掃描 search（占全部 guarded read 的
    99.7 %）全部發生在 t = 300 s；所有被觸碰 slot 的 `last_access` 相等，
    `RAM::do_evict_lru()` 的嚴格 `<` 在全平手時固定選中物理索引最小的 slot，
    DRAM 退化成「(容量−1) 個凍結頁 + 1 個輪替 slot」。
    **後果**：`ram_misses` / `ram_lru_evictions` 有 95–99 % 來自掃描階段，
    不能當「主迴圈的逐出強度」讀（主迴圈的真實 miss 見 §10.0 的推估欄）。
    **不受影響**：SDC、平均 op 延遲、`n_flip_events` 三者都只在主迴圈計數。
    **本批未修改任何 v2 或 driver 程式碼**（v2 對本實驗層是唯讀相依，
    且改動會使 E1′–E4′ 無法逐格比較）。E1′–E4′ 完全不受影響——那批
    `ram_misses = 0`。

### 尚未回答 / 值得後續（更新）

- §9 的「`CTRL_CRC` 在 RAM 受限下的表現未測」**已由 E5′ 回答**（第 12–15 點）。
- **`CTRL_CRC` + `sanity_always` 的疊加**仍未跑。E5′ 讓這件事更值得做：
  `SANITY` 的絕對延遲在 E5′ 的每一格都比 `CTRL_CRC` 低 2.47–2.50 µs，
  兩者的偵測面互補，疊加成本 ≈ `t_sanity` 50 ns。
- **`values[]` 的分層保護**：E6a′ 顯示「不保護 `values[]` 的代價」＝活 payload
  比例，隨 order 從 1.24 %（order 8）到 36.04 %（order 253）——
  **混合方案（`CTRL_CRC` + 只對熱門葉做 `FULL_CRC`）在高 order 才划算，
  在低 order 幾乎沒有可回收的空間。**
- **E5′ 的 r2（Ramulator2）複本沒跑。** RAM 受限是唯一一個「延遲被 SSD miss
  而非 write-through 主導」的條件（§8 指出 r2 在其他條件下延遲資訊量有限），
  所以這裡反而是 cycle-accurate 後端最可能顯出差異的地方。
- **> 5M keys 的規模軸**受限於單 run wall（10M 的 `FULL_CRC` > 600 s）。
  若要推到 10M–50M，需要先把完整性掃描改成抽樣，或把 `n_ops` 與掃描規模解耦。

## 14. E7′ — key 稀疏度（結構不變量 vs 真實檢查碼）

資料在 `results/e7_dbscale.csv`（125 列 = 5 stride × 5 scheme × 5 seeds），
腳本 `scripts/run_e7_db.sh`。**本節由 E1′ 的一項再分析催生，不在原始 E1–E6 規劃內。**

### 14.0 為什麼要做這個實驗

把 E1′ 的 `SANITY`（零可靠記憶體的結構不變量檢查）與 `CTRL_CRC`
（header+keys+children 的真實 CRC）逐 λ 攤開比對真陽性數：

| λ | `SANITY` tp | `CTRL_CRC` tp | 差距 |
|---|---|---|---|
| 1e-4 | 64 | 65 | +1.6 % |
| 3e-4 | 175 | 175 | 0 % |
| 1e-3 | 564 | 569 | +0.9 % |
| 3e-3 | 1 712 | 1 729 | +1.0 % |
| 1e-2 | 5 057 | 5 097 | +0.8 % |
| 3e-2 | 11 463 | 11 666 | +1.8 % |

**兩者偵測到的幾乎是同一個集合**（差距全在 2 % 內），但 `CTRL_CRC`
在 λ=3e-3 多付 24 個百分點的延遲（+67.9 % vs +44.1 %）。
照 E1′ 的條件看，`CTRL_CRC` 相對免費的 `SANITY` 幾乎不值得。

**假說**：這是 workload 的產物，不是方案的性質。E1′ 的 key 是
**密集連續整數**（`std::iota(0..prefill-1)` 打亂插入順序，但 key *集合*
是稠密的；主迴圈再 `prefill_keys + counter++` 連續 append），
所以葉內相鄰 key 的間距 ≈ 1。`sanity_check()` 強制「keys 嚴格遞增」——
間距為 1 時，key 內*任何*一個位元翻轉都讓它位移 ≥ 1 而破壞嚴格遞增，
於是這條免費不變量的行為近似一個**涵蓋 key 陣列的免費檢查碼**。
這是 `SANITY` 的最佳情況，也正好是 `CTRL_CRC` 最難展現價值的情況。

**解析預測**：相鄰 key 間距為 `2^k` 時，位於第 `b < k` 位元的翻轉使 key
位移 `2^b < 2^k`，不足以越過鄰居 → 排序不變 → `SANITY` 看不見；
`b ≳ k` 才會破壞排序。故 `SANITY` 對 key 區翻轉的相對偵測率應約以
`(64−k)/64` 衰減，而 `CTRL_CRC` 作為真實檢查碼應完全不受影響。

（同一機制曾在本專案的 SQLite 實驗中以另一種基質觀察到：key 密度是
native/結構偵測能力的隱藏變數——dense 下 separator/rowid 翻轉全被抓，
sparse 下低位元 recall 掉到 0.57、34 % 的 leaf rowid 毀損靜默通過，
且 recall 隨位元位置單調上升。E7′ 在 B+ 樹上重現並量化同一現象。）

### 14.1 程式改動與回歸保證

新增 `ExpConfig::key_stride_log2`（CLI `--key_stride_log2=<n>`，預設 0），
把稠密索引映射成實際 key：`key = index << key_stride_log2`，
在 prefill、主迴圈 insert、參照 `std::map` 三處一致套用。
search-miss key 改為**保證不是 stride 的倍數**，因此在任何 stride 下都
確定落在插入集合之外（原本的 `1e9 + uniform(0,1e9)` 在大 stride 下
會與真實 key 空間重疊，導致「查不到」被誤計）。

**回歸保證（本批最重要的健全性檢查）**：`key_stride_log2 = 0` 必須是
完全的 no-op。以 λ=3e-3 / order 253 / 1M keys / 5 seeds 重跑並與
`e1_dbscale.csv` 對應列逐欄比對：**425 欄全部相同，0 欄相異**
（比對 `tp/fn/tn/fp/n_wrong_undetected/n_wrong_total/n_flip_events/
n_recoveries/n_pages_allocated/n_final_integrity_errors/n_would_crash/
n_poisoned_writes/n_searches/n_guarded_reads/tree_height` 與兩個歸因欄）。
因此 E7′ 的 `stride=0` 欄**就是** E1′ 的 λ=3e-3 欄，不是另一次抽樣。

### 14.2 資料品質檢查

**通過**：

1. `stride=0` 對 E1′ 的 425 欄逐欄重現（見 §14.1）。
2. **`CTRL_CRC` 與 `FULL_CRC` 的每一個數字在五個 stride 間完全不變**
   （`CTRL_CRC`：tp 1728.6、SDC 6.069e-4、延遲 17.6262 µs；
   `FULL_CRC`：tp 4489.8、SDC 0、延遲 28.5590 µs——五格全同）。
   這是本實驗的內建對照組：故障流由 seed 決定、與 key 語意無關，
   所以「與語意無關的檢查碼」理應逐位元不動。它確實不動，
   證明 stride 只改變了 workload 的語意、沒有擾動注入或計時。
3. 歸因不變量 `ctrl_only + payload_only + mixed + ssd_header == tp + fn`
   逐列成立。

**警告**：

1. **`kb_seen_*` / `kb_tp_*` 直方圖是「讀取加權」而非「事件加權」。**
   未被偵測的毀損頁會留在 RAM 裡被反覆讀取，每讀一次就再計一次 `seen`；
   被偵測到的頁第一次讀取就修復、不再累計。實測放大倍率約 **365–386 ×**
   （盲區位元 `seen` 中位數 ~34 000 vs 可偵測位元 ~88）。
   **因此直方圖的比值不可當作 per-event recall 引用**；
   可以引用的是「哪些位元的 `tp` 恆為 0」（盲區邊界）與邊界的移動方向。
2. `NONE` 的 SDC 隨 stride 單調*下降*（1.013e-1 → 2.426e-2，−76 %），
   `n_final_integrity_errors` 同步 113 585 → 47 017。**本節未查明原因**；
   最合理的猜測是稀疏 key 下被污染的 separator 值更可能落在
   「實際被查詢的 key 集合」之外而不再誤導查詢，但這是假設、未驗證。
   這使得跨 stride 比較 `SANITY` 的**絕對** SDC 時混入了 workload 效應——
   因此 §14.3 的主結論一律採用 **`SANITY` / `CTRL_CRC` 的比值**
   （同一 stride 內、同一故障流的配對比較），而非絕對值。

### 14.5 位元位置直方圖：機制被修正成更強的版本

`SANITY` 的 `tp` 依「key 內被翻轉的位元位置」展開後，出現清楚的
**盲區 + 邊界右移**結構（`tp` 恆為 0 的位元 = 盲區）：

| stride | 葉 gap | log₂ | 內部 separator gap = 葉 gap × fanout | log₂ | **實測盲區邊緣** |
|---|---|---|---|---|---|
| 2^0 | 1 | 0.0 | 174 | 7.4 | **7** |
| 2^8 | 256 | 8.0 | 44 544 | 15.4 | **18** |
| 2^16 | 65 536 | 16.0 | 11 403 264 | 23.4 | **23** |
| 2^24 | 1.678e7 | 24.0 | 2.919e9 | 31.4 | **30** |
| 2^32 | 4.295e9 | 32.0 | 7.473e11 | 39.4 | **34** |

**實測邊緣一律跟隨「內部節點 separator 的 gap」，而不是葉子的 gap。**
這修正了 §14.0 的原始假說，並且得到一個更強的敘述：

> 即使葉子的 key 是稠密的（結構檢查的最佳情況），**內部節點的 separator
> key 本質上就是稀疏的**——它們的間距是「葉 gap × fanout」。所以在
> order 253、稠密 key 的 E1′ 條件下，`SANITY` 對每個 separator 的
> **最低約 7.4 個位元本來就是盲的**。而 separator 位於每一次搜尋的路徑上：
> 未被偵測的 separator 毀損被重複讀取的次數約為被偵測者的 **365–386 倍**。
> **免費的結構檢查，正好盲在盲了最貴的地方。**

對照組 `CTRL_CRC` 的同一張表在所有 stride、所有位元位置一律為 1.0——
檢查碼不理解語意，因此不存在盲區。

（`stride=2^0` 的盲區邊緣 7 與預測 7.4 吻合；`2^16`/`2^24` 亦然
（23 vs 23.4、30 vs 31.4）。`2^8`（18 vs 15.4）與 `2^32`（34 vs 39.4）
偏離較大，未進一步追查——`fanout=174` 是由「1M keys ÷ ~5 747 leaves」
估得的平均值而非實測分佈，且高位元格的樣本數較少。）

### 14.6 Observations（E7′）

24. **`CTRL_CRC` 相對 `SANITY` 的價值是 workload 的函數，不是常數。**
    在稠密 key（E1′ 的條件）下兩者偵測差距 1.0 %，`CTRL_CRC` 不值得多付
    24 個百分點延遲；在 stride 2^32 下 `SANITY` 只剩 `CTRL_CRC` 的
    51.5 %，且 SDC 劣化 47 %。**E1′ 單獨看會低估 `CTRL_CRC`，
    因為它剛好跑在結構不變量的最佳情況上。**

25. **`SANITY` 的偵測能力可以用一行封閉式預測。** 相對偵測率 ≈ `(64−k)/64`
    （k = log₂ 相鄰 key 間距），五個點誤差 ≤ 1.5 pt。這代表結構不變量的
    保護力**可以在部署前從 key 分佈算出來**，不必實測——
    對「要不要為這個索引付檢查碼的錢」是可直接使用的判準。

26. **內部 separator 的盲區是結構性的，與葉 key 密度無關。** separator 間距
    = 葉間距 × fanout，所以 fanout 越大（越像真實 DB）盲區越寬：
    order 253 時即使葉 key 完全稠密，最低 ~7.4 個位元仍是盲的。
    **提高 fanout 會同時放大「傷害集中在控制平面」（§9）與
    「結構檢查對控制平面的盲區」——兩個效應同向疊加。**

27. **盲區的代價被讀取放大 365–386 倍。** 未被偵測的毀損留在 RAM 中被
    每一次經過的搜尋重複讀取；被偵測者第一次讀取即修復。
    因此「偵測率差 48 %」在端到端錯誤上的實際權重遠高於 48 %。

28. **方法論：`CTRL_CRC`/`FULL_CRC` 在五個 stride 間逐位元不變，
    是本批最有力的健全性證據。** 它證明 stride 只改動了 workload 語意，
    沒有污染故障注入、計時或計數路徑；`SANITY` 的變化因此可以歸因於
    語意本身，而不是實驗擾動。

## 15. E2b′–E2e′ — 大內部節點數下的預算軸重測

資料在 `results/e2{b,c,d,e}_dbscale.csv`（各 120 列 = 4 policy × 10 預算 × 3 seeds），
腳本 `scripts/run_e2{b,c,d,e}_db.sh`。**本節修正 §6（E2′）的一個規模缺陷。**

### 15.0 為什麼要重測

§6 的 E2′ 跑在 order 253 / 1M keys 上，該樹只有 **35 個內部節點**、樹高 3，
於是得到「512 B（滿預算的 0.7 %）就砍掉 98.7 % 的 SDC」這個結論。
問題有二：

1. **內部節點數是被扇出綁死的，不是可自由放大的變數。** order 253 時
   樹高 4 需要 > 253³ ≈ 1 600 萬 key、樹高 5 需要 > 40 億。所以在 1M keys
   下「只有 35 個內部節點」是幾何必然，該結論無法外推到內部節點多的樹。
2. **預算格點是絕對位元組**（0/128/…/69312），照 35 節點的樹設計。
   放到內部節點數千的樹上，整個格點都落在膝點左側，什麼都量不到。

**方法學修正**：定義 `B_int` = 剛好裝下全部內部節點所需位元組
（= `n_internal_total × entry_bytes`），預算改掃 `B_int` 的固定倍數
{0, 0.1, 0.25, 0.5, 0.75, 1, 2, 4} 再加 `B_full` 與 ∞。
如此每個配置的膝點都落在格點內，且四個配置可直接互相比較。
同時新增逐層節點數欄位 `n_nodes_level_0..7`（level 0 = 葉）與
`n_internal_total`，讓「內部節點佔全樹幾 %」可由資料直接驗證。

### 15.4 結論：機制不變，但「便宜」是配置特例

| 配置 | 內部節點 | 內部佔比 | 膝點位置 | 膝點 %`B_full` | BY_LEVEL@膝點 | LRU@膝點 | 領先倍數 |
|---|---|---|---|---|---|---|---|
| E2b′ | 130 | 0.44 % | **1.00 × `B_int`** | 0.44 % | 1.665e-03 | 6.869e-02 | **41.2 ×** |
| E2c′ | 1,052 | 2.29 % | **1.00 × `B_int`** | 2.29 % | 1.776e-03 | 1.304e-02 | **7.3 ×** |
| E2d′ | 4,159 | 4.44 % | **1.00 × `B_int`** | 4.44 % | 1.616e-03 | 8.733e-03 | **5.4 ×** |
| E2e′ | 16,044 | 8.28 % | **1.00 × `B_int`** | 8.28 % | 1.308e-03 | 5.193e-03 | **4.0 ×** |

**29. 膝點在四個配置全部落在 `1.00 × B_int`——精確、無例外。**
內部節點數從 130 到 16 044（123 倍）、樹高從 3 到 6，膝點都恰好是
「剛好裝得下全部內部節點」的那一格；再多給預算（2×、4× `B_int`）
對 `BY_LEVEL` 幾乎沒有額外效果（例如 E2d′：1.616e-3 → 1.480e-3 → 1.271e-3）。
**§6 的機制解釋是對的，而且是尺度不變的——只要用對單位。**

**30. 但「0.7 % 的預算就夠」是配置特例，不可外推。**
膝點佔滿預算的比例隨內部節點佔比等比放大：
0.44 % → 2.29 % → 4.44 % → 8.28 %（**18.7 倍**）。
這正好等於內部節點佔全樹的比例（0.44 % → 8.28 %），因為
每頁 entry 大小固定。**正確的敘述是「膝點 = 內部節點的儲存成本」，
而不是「膝點 ≈ 全預算的 1 %」。**

**31. `BY_LEVEL` 相對 `LRU` 的優勢隨內部節點數增加而顯著壓縮：
41.2 × → 7.3 × → 5.4 × → 4.0 ×（縮小 10.4 倍）。**
原因是 `LRU` 本來就會自然留住內部節點（它們每次搜尋都被讀到），
內部節點越多、`LRU` 的自然保留就越接近顯式的分層策略。
**§6「`BY_LEVEL` 全預算段領先」的結論仍成立（四個配置、每個預算點皆然），
但領先幅度是內部節點稀少時才有的紅利，不是恆定的。**

**32. 無保護基準 SDC 隨 order 下降而下降**（7.296e-2 → 4.145e-2 → 1.949e-2 → 1.468e-2）。
扇出越小，單一內部節點覆蓋的 key 越少，被污染時的傷害半徑越小。
這與 §11（E6a′）的密度軸結論方向一致，是同一個幾何效應的另一個切面。

## 16. E8–E12：key 稀疏度的五個延伸實驗

**動機。** §14（E7′）發現免費的結構檢查 `SANITY` 對 key 的偵測力隨 key 間距下降，
比例約為 (64−k)/64。本節用五個實驗回答四個後續問題：這個規律在真實分布下還成立嗎、
盲區到底在哪一層、盲區裡的翻轉有沒有害、以及「內部節點用 CRC、葉節點用 `SANITY`」
這個分層方案實際表現如何。

**共同配置**（同 E7′）：order 253、1M keys、30 000 ops、λ = 3e-3、`EVERY_READ`、預算無限。
全部 448 個 run；stride 0 與 `e7_dbscale.csv` / `e7_ctrlhdr.csv` 逐欄完全一致（回歸檢查通過）。
原始資料：`e8…e12_dbscale.csv`；逐實驗參數與表格：`e8_e12_findings.md`；
重算腳本：`scripts/analyze_e8_12.py`。

### 16.1 E12：無保護時 SDC 為何隨 key 變稀疏而下降（50 runs）

也就是說，`SANITY` 在內部節點上看不到的那些翻轉，有一部分本來就無害。

內部節點的邊界 = separator 間距（k + log₂ fanout ≈ k + 7.4，實測 7 / 23 / 38）。
**即使葉節點完全 dense（stride 0，葉側無盲區），內部節點仍有 7 個 bit 的盲區。**

**35a. 以事件數為分母重算的逐位元偵測率。** 上表的邊界用讀取加權的 `kb_seen` 當分母。改用同一位元在 `CTRL_CRC` 下的偵測次數（= 該位元實際被翻轉且被讀到的事件數）當分母後，無法偵測的位元數為：葉節點 0 / 16 / 32，內部節點 8 / 24 / 40（預測 7.4 / 23.4 / 39.4）。內部節點 stride 32 由 38 變為 39 是分母定義不同所致。網頁版圖表採用這個算法。

**36. 無保護時，一次內部節點翻轉造成的錯誤答案數是葉節點翻轉的約 1340 倍**
（12.86 對 0.0096，stride 0）。internal-only 的 NONE 已接近飽和（SDC 0.70），
所以這是下限。這是「錯誤向下傳播」最直接的量測。

**37. `CTRL_CRC` 剩下的 SDC 全部來自葉節點的 values[]。**
internal-only 注入下它的 SDC 恆為 0；leaf-only 下為 6.9e-4，且不隨 stride 變動。

**38. 內部節點的盲區變大，但傷害沒有跟著變大。** stride 0 → 32，
internal 的 SANITY/CTRL 比值從 0.83 降到 0.60，但 `SANITY` 每次翻轉的錯誤數
維持在 0.016–0.018。葉側則相反：每次翻轉錯誤數 0.0041 → 0.0065，
扣掉 values[] 的地板（0.0036）後是 0.0005 → 0.0029，約 6 倍。
**稀疏 key 的實際代價主要落在葉節點的 key 陣列，不是內部節點。**

### 16.3 E10：分層方案 HYBRID（100 runs）

`HYBRID` = 內部節點走 `CTRL_CRC`（佔 shadow entry），葉節點只跑 `SANITY`（不佔記憶體）。

| stride | scheme | SDC | 未偵測錯誤/run | 平均延遲 (µs) | shadow memory |
|---|---|---|---|---|---|
| 0 | SANITY | 7.18e-4 | 19.4 | 15.13 | 0 B |
| 0 | **HYBRID** | 6.44e-4 | 17.4 | 16.82 | **396 B** |
| 0 | CTRL_CRC | 6.07e-4 | 16.4 | 17.70 | 69 154 B |
| 0 | FULL_CRC | 0 | 0 | 28.56 | 69 154 B |
| 32 | SANITY | 1.058e-3 | 28.6 | 12.97 | 0 B |
| 32 | **HYBRID** | 9.70e-4 | 26.2 | 14.68 | **396 B** |
| 32 | CTRL_CRC | 6.07e-4 | 16.4 | 17.70 | 69 154 B |

`HYBRID` 補上的 SANITY→CTRL_CRC 差距：stride 0 / 8 / 16 / 24 / 32 = 67 % / 65 % / 32 % / 20 % / 20 %。

**39. 記憶體：符合預期。** 396 B = 33 個內部節點 × 12 B，正好是 `B_int`，
比 `CTRL_CRC` 少 99.4 %。

**40. dense key 下：符合預期。** `HYBRID` 用 0.6 % 的記憶體取得 `CTRL_CRC` 三分之二的 SDC 改善。

**41. 稀疏 key 下：不符合預期。** `HYBRID` 只補上 20 % 的差距，
因為（發現 38）稀疏 key 的代價在葉節點 key 陣列，而 `HYBRID` 對葉節點只有 `SANITY`。

**42. 延遲：不符合預期。** `HYBRID` 16.82 µs，接近 `CTRL_CRC`（17.70）而非 `SANITY`（15.13）。
樹高 3，每次搜尋三次讀取中有兩次是內部節點，都要算 CRC。

**統計註記。** 每格 5 seeds，差距的絕對量很小（每 run 27 048 次搜尋中差 2–3 個錯誤答案）。
`HYBRID` ≤ `SANITY` 在 25 組配對中成立 25 次（21 勝 4 平 0 負），方向一致；
paired bootstrap 95 % CI 在五個 stride 都不含 0。但 n = 5 的 bootstrap CI 偏窄，
效果量請以「每 run 少 2–3 個錯誤答案」理解，不宜解讀為大幅改善。

### 16.4 E8：真實 key 分布（100 runs）

| key 分布 | 實測 SANITY/CTRL tp | 公式預測（方向感知） | 公式預測（min-gap） | SANITY SDC | CTRL_CRC SDC |
|---|---|---|---|---|---|
| clustered（1000 群 × 1000 連號） | 0.980 | 1.000 | 1.000 | 7.40e-4 | 6.07e-4 |
| geomgap，平均間距 2⁸ | 0.865 | 0.880 | 0.911 | 9.92e-4 | 6.07e-4 |
| geomgap，平均間距 2¹⁶ | 0.750 | 0.755 | 0.786 | 8.73e-4 | 6.07e-4 |
| geomgap，平均間距 2²⁴ | 0.632 | 0.630 | 0.661 | 9.62e-4 | 6.07e-4 |
| random64（雜湊／UUID 類） | **0.338** | 0.332 | 0.364 | 1.24e-3 | 6.07e-4 |

**43. 公式在非均勻分布下仍成立。** 方向感知版（bit 由 0 翻 1 看右鄰、由 1 翻 0 看左鄰）
在五種分布上誤差 ≤ 2.0 pp；簡化的 min-gap 版系統性偏高約 3 pp。

**44. 決定偵測力的是平均間距，不是間距的變異。** geomgap@k 與固定 stride k 的比值差 ≤ 0.6 pp。

**45. 雜湊型 key 是最差情況。** random64 下 `SANITY` 只抓到 `CTRL_CRC` 的三分之一，
SDC 為其兩倍（1.24e-3 對 6.07e-4）。clustered 則幾乎與 dense 相同（0.980）。

### 16.5 E9：fanout × stride（144 runs，200k keys）

**46. tp 比值規律對 order 64 / 253 成立**（與 (64−k)/64 差 1–7 pp）；
order 16 在每個 stride 都約為預測值的 0.78 倍。可能原因是 order 16 的節點很小，
`SANITY` 完全看不到的 SSD header 與 child pointer 佔 `CTRL_CRC` 涵蓋範圍的比例變大；尚未驗證。

**47. E9 的盲區邊界量測受混合效應干擾，不能用來檢驗 separator 間距假說。**
`kb_*` 直方圖把葉節點與內部節點的 key 翻轉混在一起，邊界落在兩者之間
（order 253：stride 8/16/24 → 12/15/23，預測 15.4/23.4/31.4）。
200k keys 下 order 253 只有 8 個內部節點，葉側事件佔比高於 E7′。
**分層後的 E11（發現 35）才是這個假說的正確檢驗，且結果為成立。**
order 16 在 stride > 0 的邊界因事件數不足而無法量測。

### 16.6 小結

- `SANITY` 的偵測力可由 key 分布事先算出（發現 43），雜湊型 key 下降到 `CTRL_CRC` 的三分之一。
- 內部節點即使在 dense key 下也有盲區（發現 35），且無保護時單次翻轉的傷害是葉節點的 ≥ 1340 倍（發現 36）。
- 但加上 `SANITY` 後，內部節點盲區的殘餘傷害不隨稀疏度成長（發現 38）；稀疏 key 的代價在葉節點 key 陣列。
- 因此「只保護內部節點」的 `HYBRID` 在 dense key 下划算（發現 40），在稀疏 key 下不夠（發現 41）。
  稀疏 key 的合理下一步是「內部節點 CRC ＋ 葉節點僅 keys[] CRC」，values[] 仍留在保護範圍外；本節未實作。

### 16.7 已知限制

- E11 的 internal-only 使用 50 倍 λ，翻轉會在同一頁累積；NONE 已近飽和。
- NONE 的 seed 3 在 E9 / E12 有樹走訪警告（毀損節點被寫回後 oracle 走訪失敗）；逐層節點數來自配置計數器，不受影響。
- `pred_sanity_*` 以整個 key 集合的相鄰 key 計算，忽略葉節點邊界。
- E10 / E12 每格 5 seeds，E9 / E11 每格 3 seeds。

以無清洗估算的上限約 24 個，方向與量級相符，但未逐事件驗證。

四種 key 分布下是同一個翻轉序列造成的同一事件，不是四次獨立事件，應以中位數解讀。

**51. 配上內部節點 CRC（`HYBRID`）後，葉節點 key 造成的「找不到」幾乎消失**：
2³² 時 7.8 → 0.6（右側，CI [+4.4, +10.8]），random64 時 12.0 → 1.2（兩側，CI [+8.6, +13.2]）。
與同樣大小樹上的 `CTRL_CRC` 相比只差 0.8–2.6 個錯誤答案（原本差 9.8 / 14.4）。
但因 (c)，合計只在 random64 兩側明顯下降（30.8 → 19.2）。

**52. 成本很高。** 頁數 2–3 倍，平均延遲 2–3 倍（每次插入要多寫 dummy，回復次數也隨翻轉數增加）。
以「把 dummy 當一般 key 插入」的形式，這個方案不划算。不增加頁數的空槽版（E14）尚未測試。

### 17.3 頁內 CRC：不用可靠記憶體，結果與 shadow store 版完全相同

| 方案 | SDC | 平均延遲 µs | 可靠記憶體 |
|---|---|---|---|
| SANITY | 7.18e-4 | 15.13 | 0 B |
| HYBRID | 6.44e-4 | 16.82 | 396 B |
| CTRL_CRC | 6.07e-4 | 17.70 | 69 153 B |
| **INPAGE_CTRL** | **6.07e-4** | **17.64** | **0 B** |
| FULL_CRC | 0 | 28.56 | 69 153 B |
| **INPAGE_FULL** | **0** | **28.49** | **0 B** |

（間距 2⁰；間距 2³² 與 random64 的 INPAGE 數字相同，因為 CRC 與 key 數值無關。）

**53. 30 個 run 中，頁內 CRC 的錯誤答案數逐 seed 與對應的 shadow store 方案完全相同（30 / 30）。**

可靠記憶體對偵測沒有額外價值：同樣的保護可以用頁內 4 bytes 取得。
§6、§15「可靠記憶體預算該優先給內部節點」的結論在數值上仍成立，但其前提（偵測需要可靠記憶體）
在此模型下不成立。不受影響的部分：內部節點翻轉的傷害放大（§16 發現 36）、
結構檢查的盲區與 key 分布的關係（§14、§16）、以及「該對哪些層付 CRC 計算時間」的延遲取捨。

### 17.4 已知限制

- 6 個 `SANITY` 加 dummy 的 run 在期末樹走訪檢查失敗；逐層節點數取自配置計數器，不受影響。
- 每格 5 seeds；2–4 個錯誤答案的差距在 seed 變異範圍內，結論以配對檢定與拆項為準。
- 頁內 CRC 能放在頁尾是因為 order 253 的節點最多用到 4088 bytes；其他 order 需保留 4 bytes。

它對葉節點中間的 key 沒有幫助，與模型一致。小節點（order 16）受益最大。

**56. 模型預測「有害的內部翻轉全數抓到」不完全成立。** 實測只翻轉內部節點時每 1000 次翻轉仍有 0.55–0.96 個錯誤。
推測是分隔點向上漂移時，被導錯的搜尋走到的左子節點看起來仍合法，要等有人走到右子節點才會發現；未逐事件驗證。

**57. 範圍檢查能發現但不一定能修復。** 內部節點高注入率下每 run 有 1.3k–3.5k 次警報、439–1 147 次放棄。
診斷顯示壞掉的內部節點會在 split 時被寫回 SSD，從 SSD 重載只會載回壞的版本。

### 18.2 E18：對齊檢查（key 為固定倍數時）

| key | SANITY | 加對齊檢查 | 差異（95 % CI） | 葉 key 偵測比例 |
|---|---|---|---|---|
| 2⁸ | 7.6 + 17.4 = 25.0 | 5.6 + 17.2 = 22.8 | +2.2 [+1.0, +3.2] | 0.849 → 0.992 |
| 2¹⁶ | 6.6 + 17.4 = 24.0 | 2.4 + 17.2 = 19.6 | +4.4 [+2.4, +6.2] | 0.722 → 0.994 |
| 2³² | 10.2 + 18.4 = 28.6 | 2.2 + 17.0 = 19.2 | +9.4 [+6.8, +12.8] | 0.468 → 0.996 |

**58. 對齊檢查把稀疏 key 拉回連號 key 的水準（19.4），不增加頁數。**
延遲 15.14 µs，與連號 key 的 `SANITY`（15.13）相同；比原本稀疏時高是因為抓到並修復的錯誤變多。
E21 的「除掉間距」做法（2³² → 連號）結果與 2⁰ 逐欄完全相同（2.0 + 17.4 = 19.4），兩者等效。

### 18.3 E19：空槽 dummy key（頁數不變）

| key | SANITY | 右側 dummy | 差異（95 % CI） | 葉 key 偵測比例 | 有 dummy 的 key 比例 |
|---|---|---|---|---|---|
| 2¹⁶ | 6.6 + 17.4 = 24.0 | 5.0 + 18.0 = 23.0 | +1.0 [−2.8, +4.2] | 0.722 → 0.844 | 45 % |
| 2³² | 10.2 + 18.4 = 28.6 | 8.0 + 18.4 = 26.4 | +2.2 [−2.8, +8.4] | 0.468 → 0.692 | 45 % |

**59. 空槽 dummy 提高了偵測比例，但端到端差異在 5 個 seed 下不顯著。**
空槽只夠讓 45 % 的 key 有 dummy；兩側版本只覆蓋 22 %，不比右側版好。頁數不變，延遲多 1.6–1.9 µs（重載次數增加）。

### 18.4 E20：免費手段全部組合

| key | SANITY | 範圍 + 空槽 dummy | 範圍 + 空槽 dummy + 對齊 |
|---|---|---|---|
| 2⁰ | 2.0 + 17.4 = 19.4 | 0.0 + 17.8 = 17.8 | 不適用 |
| 2¹⁶ | 6.6 + 17.4 = 24.0 | 2.6 + 18.0 = 20.6 | **0.0 + 15.2 = 15.2** |
| 2³² | 10.2 + 18.4 = 28.6 | 5.6 + 18.4 = 24.0 | **0.0 + 15.2 = 15.2** |
| random64 | 14.8 + 18.8 = 33.6 | 9.8 + 19.6 = 29.4 | 不適用 |

**60. 有規律的 key：三項全開後「找不到」在 10 個 run 中全部為 0**（2³²：+13.4 [+8.8, +18.6]），
剩下的只有結構檢查碰不到的 value 錯誤。頁數不變；延遲 18.5 µs（重載次數約 3 000 次）。

**61. 無規律的 key：免費手段只拿到約三分之一，且不顯著**（random64「找不到」14.8 → 9.8，CI [−0.6, +12.4]）。

### 18.5 E21：把 key 映射到密集範圍

無規律的 key 以 hash 分配到 M = N/α 格的開放定址表，樹的 key 用格子編號；每個 key 佔兩筆相鄰資料
（原 key、value）。查詢時以「存著的原 key 重新 hash 後位置是否對得上」做自我驗證。

| 做法 | 找不到 + value 錯 | 頁數 | 延遲 µs | 每次命中 / 落空的探查數 |
|---|---|---|---|---|
| random64 原樣，SANITY | 14.8 + 18.8 = 33.6 | 5 762 | 12.20 | 1 / 1 |
| random64 原樣加右側 dummy（同樣 2 倍大的對照） | 12.6 + 22.8 = 35.4 | 11 519 | 25.53 | 1 / 1 |
| hash 映射 α = 0.25，SANITY | 4.6 + 18.0 = 22.6 | 11 504 | 28.21 | 1.17 / 1.40 |
| hash 映射 α = 0.5，SANITY | 4.6 + 21.4 = 26.0 | 11 493 | 28.55 | 1.50 / 2.57 |
| hash 映射 α = 0.75，SANITY | 3.4 + 18.0 = 21.4 | 11 521 | 29.42 | 2.50 / 8.18 |
| hash 映射，無保護 | 1 117 – 1 625 | 約 11 500 | 約 21 | — |

**62. hash 映射讓無規律 key 的「找不到」減少七成以上**（14.8 → 3.4–4.6；對原樣與對 2 倍大對照皆顯著）。
α 之間沒有可分辨的趨勢；探查數與模型一致。

**63. 代價：頁數 2 倍、延遲約 2.3 倍、必須另存原 key、失去依 key 順序掃描的能力。**

**64. hash 映射不可單獨使用。** 無保護時錯誤由 98.8 暴增到 1 100 以上。

**65. 一個未解的異常。** 2³² 的 key 套用 hash 映射（α = 0.5）時，seed 2 發生連續重載（151 萬次回復、242 個「找不到」），
其餘四個 seed 為 16–25。原因未查明。

### 18.6 小結：只用 SANITY 時該怎麼處理稀疏 key

| key 類型 | 建議 | 「找不到」 | 成本 |
|---|---|---|---|
| 任何 key | 加父子範圍檢查 | 少 2.4–3.0，內部節點錯誤近乎消失 | 無 |
| 有固定規律 | 對齊檢查，或直接換算成連號 | 10.2 → 2.2；再加範圍檢查與空槽 dummy → 0 | 無 |
| 無規律 | hash 映射到密集範圍 | 14.8 → 3.4–4.6 | 頁數 2 倍、延遲 2.3 倍、失去順序掃描 |
| 無規律，不願付成本 | 範圍檢查 + 空槽 dummy | 14.8 → 9.8（不顯著） | 頁數不變 |

所有方案都碰不到 value 錯誤（每 run 15–21 個），這是結構檢查的地板。
在空隙中間放 dummy（E13 的對照組）每多一倍 dummy 只多看到 1 個位元，不建議。
